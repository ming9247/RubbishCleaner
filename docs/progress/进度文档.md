## 4. 开发过程中发现并修复的真实缺陷

> 这些都不是"写之前就想到"的，而是**跑起来之后**暴露的，值得记录。

| # | 现象 | 根因 | 修复 |
|---|------|------|------|
| 1 | `scvhost` 未被识别为伪装 | 普通 Levenshtein 对"相邻换位"计 2 分 | 改用 Damerau-Levenshtein（OSA），换位计 1 |
| 2 | **进程直接崩溃**（AccessViolation） | `WINTRUST_CATALOG_INFO.pcCatalogContext` 传了目录枚举句柄 | 该字段类型是 `PCATALOG_INFO`，必须传 `NULL`；同时把已打开的文件句柄传给 `hMemberFile` |
| 3 | 大量微软系统服务显示"无签名"→ 误判高风险 | `spoolsv.exe`、`SearchIndexer.exe` 等是**目录签名**，`CreateFromSignedFile` 看不到 | 增加 `WinVerifyTrust` + `CryptCATAdmin*` 目录签名校验 |
| 4 | NVIDIA / Intel 正规驱动服务被判高风险（85 分） | 服务天然无窗口、无桌面图标、无开始菜单，三条规则各加 25/15/15 | 引入"纯服务型"判定，三条规则标记为 `NotApplicable` |
| 5 | 修复 4 之后分数仍然是 85 | `ScoreItem.Contribution` 只看 `Hit`，没看 `NotApplicable` | `Contribution` 改为 `Hit && !NotApplicable`；`RuleCount` 同步排除 |
| 6 | 扫描耗时 3.1 秒 | 每个文件都做一次目录枚举 + 签名校验，且 `$MFT` 类操作串行 | 路径级签名缓存 + 并行化；修复后 **420 ms**（7 倍提升） |
| 7 | PowerShell 脚本中文乱码报语法错误 | Windows PowerShell 5.1 把无 BOM 的 UTF-8 当 ANSI | 脚本统一保存为 UTF-8 **带 BOM** |
| 8 | 加图标后启动即崩（XamlParseException，行 10） | `ApplicationIcon` 只把图标写进 exe 资源段，WPF 的 `Icon`/`Image` 取不到 | csproj 里补 `<Resource Include="app.ico" />`，URI 用 `/app.ico` |
| 9 | 表头列名全部消失，只剩一个 ▼ | `ContentControl.Content` 是 `object`，`Binding.StringFormat` 只在目标为 `string` 时生效 | ViewModel 里直接拼好 `"等级 ▼"` 字符串再绑定 |
| 10 | 发行商文字压到分数列上 | `StackPanel` 不按列宽裁剪子元素，长文本溢出到相邻列 | 改用 `Grid` + `TextTrimming`，真正按列约束宽度 |
| 11 | 表头与列表内容逐列错位 | ListBox 垂直滚动条占掉行内容宽度，表头没预留 | 按 `SystemParameters.VerticalScrollBarWidth` 动态补右侧留白 |
| 12 | 高分屏笔记本上窗口超出屏幕 | XAML 写死 `Width=1180`，150% DPI 下逻辑工作区只有 1280×680 | 启动时按 `SystemParameters.WorkArea` 收缩并重新居中 |
| 13 | 测试断言"点 Score 列应回到降序"失败 | **测试写错了**：Score 本就是默认激活列，点它应是"翻转"而非"切到新列" | 修正测试，并单独补一条"默认列翻转"用例 |
| 14 | WorkBuddy 两条**指向已删路径**的僵尸启动项被判 70 分"疑似" | 程序已不存在，"未签名/无窗口/无图标"全是伪信号，把残留误算成风险 | 新增失效启动项建模：`ORPHAN_STARTUP` 权重 0，其余规则标记不适用；UI 增加「残留启动项」分组 |
| 15 | Autodesk 的 `AdskAccessService` 等云服务被判 "疑似" | 无界面自启动的云服务天然没有桌面/开始菜单入口 | 按产品文档"知名厂商签名→安全"，加 `signer: Autodesk` 等正规厂商签名白名单 |
| 16 | 「残留启动项（6）」按钮永远灰着 | `RelayCommand.CanExecute` 依赖 `OrphanCount`，扫描前为 0，之后没触发重新求值 | 扫描完成后调用 `CommandManager.InvalidateRequerySuggested()` |
| 17 | 普通权限脚本点击提权程序的按钮无效果 | UIPI 隔离：低完整性进程的合成鼠标输入被丢弃 | 不再依赖跨权限 UI 自动化，改为直接驱动 ViewModel 做集成测试 |
| 18 | "有残留"但清理按钮提示"无可清理项" | 残留 ≠ 可清理：服务类残留（Winstep）被 `BuildPlan` 正确拒绝 | **不是 bug**。反而是安全闸门生效的证明；测试按"可清理项"精确判断 |
| 19 | 清理测试第二次运行失败 | 第一次清理已把机器上的 Run 类残留删干净，测试前提不再成立 | 测试内先判断"是否存在可清理项"，没有则跳过而非失败 |
| 20 | 标准用户下 USN 枚举拿到 **0 条记录**，err=38 | `HighUsn` 传了 `ulong.MaxValue`，内核把整个范围判为空 | 改传 `long.MaxValue`；注释写明这个坑 |
| 21 | 提权也没用，卷句柄还是拒绝访问 | 一开始以为"提权后就能读卷"，实际是先要确认 `IsElevated`；标准用户下任何访问权限组合都拿到 err=5 | 用 `CompositeVolumeFileIndex` 显式降级，并把实际索引方式展示给用户 |
| 22 | 若按"目录名像不像已卸载软件"判残留，会把 NVIDIA Corporation / Code / Tencent 全判成残留 | 名字匹配只对 21/306 个目录有效，其余 285 个大多是**已装软件的公共目录** | 改判定哲学：只信硬痕迹（孤儿卸载程序 / 失效启动项落点），名字匹配只用于"证明有主"（ADR-030） |
| 23 | 父目录被判成残留，而它的子目录里是**在用的**已装软件 | 认领判定只做了单向（目录位于认领路径之下） | 改成双向：目录**包含**认领路径也算有主（ADR-032）。本机实例：`Program Files\OEM` |
| 24 | `Path.GetFullPath` 把相对路径静默补全，导致"相对路径一律拒绝"这道闸门失效 | 先调用 `GetFullPath` 再调用 `IsPathRooted`，检查的是补全后的路径 | 必须在补全<b>之前</b>判断原始输入（已有对应单测兜住） |
| 25 | 回收站清理"成功"了，但实际上永久删除了 | `FOF_ALLOWUNDO` 在没有回收站的卷（网络盘/可移动盘）上 shell 会静默降级成永久删除且返回 0 | 提前拒绝非 `DriveType.Fixed` 的卷（ADR-034） |
| 26 | 清理完后状态栏立刻被"扫描完成"覆盖，用户看不到清理结果 | 清理后会重新扫描刷新列表，而重扫会覆盖 `StatusText` | 重扫之后把清理结论写回去 |
| 27 | 清理按钮显示"可清理 5 项"但实际只清了 3 个 | `CleanableCount` 只看安全闸门，没看置信度 | 两个条件都要：通过闸门**且**置信度为 High |
