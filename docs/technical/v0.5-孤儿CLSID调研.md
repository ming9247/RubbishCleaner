# v0.5 调研 —— 孤儿 CLSID / COM 组件的可判定性

> 调研人：Lead（原计划的调研成员两次在落盘前中断，本文档由 Lead 用自己的实测数据完成）
> 日期：2026-10-25　|　性质：**只读调研，未改任何注册表**
> 结论：**不做自动清理。最多做「报告级」提示，且必须放弃文件存在性判据。**

---

## 一、结论先行

**「一个 CLSID 是否已经没有主人」在注册表层无法可靠判定。** 具体分三层说：

| 层面 | 结论 |
|---|---|
| 技术上能否找出「指向已消失文件的 CLSID」 | **能，但要先跨过两个致命陷阱**（见 §三）；跨过之后本机只剩 15 个候选 |
| 这 15 个候选是不是「该删的残留」 | **无法判定**。实测里它们是「活软件的升级残留」和「Windows 自有组件的暂时缺失」，没有一个是已卸载第三方软件的残留 |
| 删掉它们是否安全 | **对 Windows 自有的键不安全**：文件今天不在，不代表 Windows Update 明天不会把它装回来；键删了、文件回来了，功能就坏了 |

一句话：**能算出来的东西不值得删，值得删的东西算不出来。**

v0.4 能做成「MSI 孤儿 Uninstall 条目」，是因为 Windows Installer 自己维护了一个权威数据库
（`MsiQueryProductState` + `MsiEnumProductsEx`），判据是问系统要答案。
CLSID 没有对应物：**Windows 不维护「这个 CLSID 被谁引用」的计数**，
所以任何判定都只能靠启发式拼凑，而启发式正是 v0.3 实测过误报率 93% 的那条老路。

## 二、CLSID 的引用来源清单

| 引用来源 | 检测方法 | 可靠性 | 备注 |
|---|---|---|---|
| `InprocServer32` / `LocalServer32` / `InprocHandler32` 指向的文件 | 展开环境变量后查文件存在性 | **低**（两个陷阱，见 §三） | 这是最直觉的判据，实测 97.6% 的「缺失」是误判 |
| `TypeLib` 子键 | 查 `HKCR\TypeLib\{guid}` 是否存在、对应文件是否存在 | 低 | 本机 15 个候选全部没有 TypeLib 子键，救不了判定 |
| `ProgID` 值 / `HKCR\{ProgID}\CLSID` 反向映射 | 双向查 | 低 | 同上，候选里一个都没有 |
| `AppID`（DCOM） | 查 `HKCR\AppID\{guid}` | 低 | 同上 |
| `TreatAs` / `AutoTreatAs` 指向 | 被指向方删除会破坏重定向 | 与判定无关，但是删除风险的一部分 | 实测存在（如 Office 旧 CLSID 重定向到新 CLSID），遍历时必须当作「有主」 |
| 文件关联 `.ext → OpenWithProgids → ProgID → CLSID` | 链式查 | 低 | 由文件关联调研覆盖（另一份文档） |
| 服务 / 计划任务 / 启动项里的 GUID 字符串 | 全注册表文本搜索 | **不可行**：实测一次 16.2 秒（§三.4） | |
| COM 激活时的运行期引用（ROT、运行中的进程） | 无法从注册表读 | 不可行 | |
| **「这个 CLSID 被谁引用」的权威计数** | **不存在** | — | 这是与 v0.4 的本质差异：MSI 有数据库，COM 没有任何等价物 |

补充：`SharedDLLs`（`HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\SharedDLLs`）
看名字像引用计数，实际由各安装器自行维护、大量不更新，**不可信**（行业共识，也符合直觉：
没有安装器 API 强制它准确）。不能当权威来源。

## 三、真机实测

### 1. 规模

```powershell
(Get-ChildItem 'Registry::HKEY_CLASSES_ROOT\CLSID').Count          # → 12779
(Get-ChildItem 'Registry::HKEY_CLASSES_ROOT\WOW6432Node\CLSID').Count  # → 6314
```

### 2. 直觉判据的第一版结果：720 个「孤儿」—— 其中 705 个是误判

第一版探针：取 `InprocServer32` 默认值 → 展开环境变量 → `Test-Path`。

```
检查了 11520 个有 InprocServer32 的 CLSID，其中「文件不存在」720 个
按缺失 DLL 归类：mscoree.dll 287 个、axdb.dll 163 个、AcPEXCtl.arx 50 个、combase.dll 17 个 …
```

`mscoree.dll`（.NET CLR 派发器）和 `combase.dll`（COM 基础设施）都是**系统 DLL，好好的**。
陷阱在于：**注册表里大量 InprocServer32 写的是裸文件名而不是绝对路径**，
COM 加载时按标准 DLL 搜索路径（应用目录 → System32 → …）解析。
`Test-Path 'mscoree.dll'` 永远是 false，但它不是孤儿——是探针错了。

修正：先区分「绝对路径」（10815 个）与「裸文件名」（705 个），只对前者做存在性检查：

```
绝对路径且文件不存在：15 个（占 11520 的 0.13%）
```

**教训**：与 v0.3 的「按目录名猜残留误报率 93%」同构——直觉判据的第一版数字几乎全是噪声。
如果按第一版直接做清理，会删掉 705 个健康键，其中 287 个是 .NET 派发器的代理注册。

### 3. 这 15 个候选是什么

| 指向 | 数量 | 实际身份 |
|---|---|---|
| `C:\Program Files (x86)\Microsoft\EdgeUpdate\1.3.2xx.x\psmachine_64.dll`（各旧版本） | 11 | **Edge 更新器的升级残留** |
| `C:\Windows\System32\TetheringSettingHandler.dll` | 1 | **Windows 自有组件**（移动热点设置处理器），文件当前不在 |
| `C:\Program Files\WindowsApps\Microsoft.GamingServices_…\InstallServicePlugin.dll` | 1 | MSIX 应用旧版本残留 |
| `C:\ProgramData\CrossDevice\…` / EndNote PowerPoint 插件等 | 2 | 第三方组件 |

**Edge 案例展开**（本机实测）:

```
引用 EdgeUpdate\psmachine_64.dll 的 CLSID 共 14 个：
  11 个指向已删除的旧版本目录（1.3.265.7 ~ 1.3.299.15）
   3 个指向当前版本 1.3.303.7（存在、正常）
EdgeUpdate 目录现存：1.3.299.15、1.3.303.7
```

也就是说：**软件活着、正在正常工作，旧版本的注册只是升级后没清**。
这类键删掉确实无害，但关键在于——

> **「升级残留」和「卸载残留」在文件存在性判据下长得一模一样。**
> 判据无法区分「这个软件还在（别管它的旧键）」和「这个软件没了（键是纯垃圾）」。

### 4. 全注册表搜索一个 GUID 的成本

```powershell
Measure-Command { reg query HKCR /f '{A530D54A-…}' /s }   # → 16.2 秒，命中 1 处
Measure-Command { reg query HKLM\SOFTWARE\Classes /f '{…}' /s }  # → 3.5 秒
```

15 个候选做一轮引用检测约 4 分钟（且只能证明「注册表里没提」，不能证明「系统不用」）。
作为对比，v0.4 的 `MsiQueryProductState` 是一次 API 调用，微秒级。

### 5. 权限陷阱：非管理员下 WindowsApps 完全不可读

| 身份 | `Test-Path` 那个 GamingServices DLL | 列 `C:\Program Files\WindowsApps` |
|---|---|---|
| 标准用户（本工具若不提权） | `False` | **0 项** |
| 管理员（本工具提权后） | `False` | **280 项** |

非提权时整个 MSIX 目录树对探针隐形：**每一个由 MSIX 应用注册的 CLSID 都会被判成孤儿**。
Windows 11 的记事本、照片、终端全是 MSIX——这条判据在标准用户下等于「把 Windows 自带应用全判成垃圾」。
提权后可读，误判消失，但工具的运行形态是先提权的（`requireAdministrator`），这一点恰好能躲过——
**前提是把「WindowsApps 下的一律不碰」写进闸门，而不是指望权限恰好正确。**

## 四、反例集（每条都能击穿一种判据）

| # | 反例 | 击穿的判据 |
|---|---|---|
| 1 | `combase.dll`、`mscoree.dll` 等 705 个裸文件名注册 | 「`Test-Path` 文件不存在 = 孤儿」——裸名按 DLL 搜索路径解析，文件好好的 |
| 2 | Edge 更新器 11 个旧版本 CLSID（软件活着） | 「指向消失的文件 = 该软件已卸载」——升级残留与卸载残留不可区分 |
| 3 | `TetheringSettingHandler.dll`（Windows 组件） | 「删掉无主键只是清噪音」——Windows Update 可能回装该文件，键没了功能就坏 |
| 4 | WindowsApps 非提权不可读 | 「文件检查结果可信」——权限不足时一切都是「不存在」 |
| 5 | `TreatAs` 重定向（实测存在，如 Office `{00020810-…}` → `{00020820-…}`） | 「只看 InprocServer32 就够」——被重定向的键删了会破坏转发链 |

## 五、如果非要做：最小安全边界（不推荐进入 v0.5 自动清理）

1. **只读报告、不清理**。把「指向缺失文件的第三方 CLSID」列出来给用户看，处置权完全交给用户——
   与产品文档「本工具不做静默删除」的原则一致。
2. 闸门（全部为硬拒绝）：
   - `WindowsApps` 路径下的一律不报（MSIX 由系统管理，且有权限陷阱）；
   - 文件在 `C:\Windows` 下、或 DLL 位于 System32/SysWOW64 的**裸文件名**一律不报；
   - 带 `TreatAs` 的、被 `TypeLib`/`ProgID`/`AppID` 引用的不报；
   - 发布者可识别为 Microsoft / 系统签名的不报；
   - HKCU 侧（`HKCU\Software\Classes\CLSID`）与 HKLM 侧分开评估。
3. 即便如此，本机收益是 **15 个键**，而 CLSID 总量 12779——扫描成本与收益完全不成比例。

## 六、建议

1. **v0.5 不做 CLSID 自动清理**。理由：判定不可靠（§一）、真实收益≈0（15 个键且多数属活软件）、
   删错的后果是不可逆的注册表损坏（.reg 备份能还原数据，但用户得先知道坏了）。
2. v0.5 的精力建议投向已被 v0.4.1 实测证明**可判定**的方向：
   服务 `ImagePath` 指向不存在文件（服务表是系统自己维护的，没有权限陷阱）；
   以及「文件与注册表状态不一致」的检测（CC Switch 案例的顺延，v0.4 日志已预留）。
3. 文件关联 / ProgID 的判定性由另一份调研文档单独评估（`v0.5-孤儿文件关联调研.md`）。
