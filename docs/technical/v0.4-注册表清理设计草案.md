# v0.4 注册表清理 —— 设计草案

> 这一版风险最高。文件删错了能从回收站还原；注册表键删错了，轻则软件报错，
> 重则系统组件加载失败。必须先定边界，再写代码。

## 一、范围：只做「孤儿 Uninstall 条目」，不做通用注册表清理

### 做

`HKLM\...\Uninstall\{GUID}` 与 `HKLM\WOW6432Node\...\Uninstall\{GUID}` 下
**MSI 产品的僵尸条目**：

| 判据 | 实测（CC Switch） |
|---|---|
| `WindowsInstaller = 1` | ✅ |
| `Classes\Installer\Products\{GUID}` 不存在 | ✅ False |
| `UserData\S-1-5-18\Products\{GUID}` 不存在 | ✅ False |

含义：Windows Installer 已经不认这个产品了，但「应用和功能」列表里还留着一条——
用户看到它、点卸载、然后报错 1639。**这是纯噪音，删掉只有好处。**

### 不做（明确划出边界）

| 不做 | 理由 |
|---|---|
| 删 `HKCR` 下的任何键 | COM 组件引用，删错导致软件加载失败 |
| 删 `HKLM\SYSTEM` | 驱动与服务，蓝屏风险 |
| 删 `Run` / `RunOnce` | v0.1.3 已做（只删值不删键），不能重复做 |
| 删 `Software\{Vendor}` 厂商根 | 里面可能挂着多个软件，无法判断归属 |
| 判「孤儿 CLSID / 文件关联」 | 需要解析 COM 引用计数，误报率不可接受，v0.5+ 再说 |
| 非 MSI 的 Uninstall 条目 | 没有可靠的「产品是否还存在」判据 |

## 二、安全模型（修订版，基于真机调研）

### 1. 判定：只信 Windows Installer 自己的回答

**不能用**「注册表 Products 键是否存在」判孤儿——实测 CC Switch 产品完好，
但那些键全都不存在（见上面的调研结果）。按那个判据会误删。

**改用双重 API 确认**：

| 检查 | API | 判定 |
|---|---|---|
| 产品状态 | `MsiQueryProductStateW(guid)` | 返回值 **2 (ABSENT)** 且 |
| 产品枚举 | `MsiEnumProductsW` 遍历 | **不含**该 GUID |

两条**同时成立**才判孤儿。任一条说"还在"就跳过。

`MsiQueryProductState` 返回值语义：

| 值 | 常量 | 含义 | 是否孤儿 |
|---|---|---|---|
| 0 | UNKNOWN | 未知（极少见） | ❌ 跳过（不确定不删） |
| 1 | ABSENT | 未安装 | ✅ 可能孤儿 |
| 2 | ABSENT | 未安装（同 1，MSI 文档两值同义） | ✅ 可能孤儿 |
| 3 | ABSENT | 未安装 | ✅ 可能孤儿 |
| 4 | ADVERTISED | 仅公告安装 | ❌ 跳过（算已安装） |
| 5 | INSTALLED | 已安装 | ❌ 绝对跳过 |
| 6 | ADVERTISED_OR_INSTALLED | 公告或已安装 | ❌ 跳过 |
| 其他 | — | 未定义 | ❌ 跳过（保守） |

### 2. 为什么还需要"删除后复核"

即使 API 说 ABSENT，删之前仍要：
1. 再查一次状态（防止扫描到确认之间的竞态）；
2. 备份 `.reg`；
3. 删键；
4. 确认键真的不存在。

### 3. 明确不做的判定

| 不做的判定 | 理由 |
|---|---|
| 「Products 键不存在 = 僵尸」 | **实测会误删**（CC Switch 案例） |
| 「InstallLocation 目录不存在 = 僵尸」 | 很多软件装在别处，InstallLocation 常为空或不准 |
| 「LocalPackage 不存在 = 僵尸」 | 用户可能清过 `C:\Windows\Installer` 缓存，产品其实还好 |
| 非 MSI 条目（无 `WindowsInstaller=1`） | 没有可靠的"产品是否存在"判据 |

## 三、清理动作

### 删除范围

只删 `Uninstall\{GUID}` 这一个键（含其下所有值）。

**不删**：

- `Installer\UserData` 下的任何东西（即使看起来是残留，MSI 内部结构不该手改）
- `Installer\Folders` 里的路径记录
- `Classes\Installer` 下任何键

### 新增闸门（在 v0.3 七道闸门基础上）

| # | 闸门 | 理由 |
|---|---|---|
| R1 | 键名必须严格匹配 `{8-4-4-4-12}` GUID | 防止误删 `Uninstall\某软件` 这类非 GUID 键 |
| R2 | 拒绝 `Uninstall` 根键本身 | 删它等于清空整个已安装列表 |
| R3 | 必须在 `Uninstall` 下且只差一层 | 防止路径拼接错误删到上层 |
| R4 | `MsiQueryProductState` 必须是 ABSENT | 见上 |
| R5 | `MsiEnumProducts` 必须不含该 GUID | 见上 |
| R6 | 备份文件必须写入成功且大小 > 0 | 备份失败就不删 |
| R7 | 删除后复核键确实不存在 | 与 `RegistryWriter` 同一约定 |

## 四、备份格式

复用 v0.1.3 的 `.reg` 机制（ADR-017），导出单个键：

```
Windows Registry Editor Version 5.00

[HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\{09CC399B-...}]
"DisplayName"="CC Switch"
"DisplayVersion"="3.16.3"
"WindowsInstaller"=dword:00000001
...
```

- 编码 **UTF-16LE + BOM**（v0.1.3 踩过：UTF-8 的中文 `reg import` 会乱码）
- 文件命名 `orphan-uninstall-{GUID}-{yyyyMMddHHmmss}.reg`
- 备份成功后**立即用 `reg import` 回读验证**（可选，但能确认真可还原）

## 五、UI

在「残留扫描」页加分组「注册表残留」：

| 列 | 内容 |
|---|---|
| 名称 | DisplayName |
| 版本 | DisplayVersion |
| 位置 | `HKLM\...\Uninstall\{GUID}` |
| 证据 | 「Windows Installer 报告该产品未安装」「该 GU ID 不在已安装产品列表中」 |

清理按钮行为与文件残留一致：先备份 → 再删 → 逐条报告。

## 六、风险与未知

1. **`MsiEnumProducts` 的 32/64 位视图**：需要两个视图各查一次，否则可能把 32 位产品误判成不在。
   实现时用 `MsiEnumProductsExW` 指定 `MSIINSTALLCONTEXT_ALL` 更稳。
2. **每用户安装的产品**：`MsiQueryProductState` 对当前用户视角判断，
   多用户机器上别的用户装的产品可能返回 ABSENT。需要 `MsiGetProductInfoExW` 按 SID 再确认。
3. **MSI 服务异常时**：API 可能返回 UNKNOWN，此时一律跳过（不确定不删）。
4. **本机实测样本太少**：CC Switch 不是僵尸（产品有效），需要另行寻找真实僵尸样本。
   如果找不到，就用"删掉 LocalPackage 后模拟"的方式造样本——但这只能测代码路径，
   不能证明判据在真实环境可靠。
