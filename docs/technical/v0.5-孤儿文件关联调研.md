# v0.5 调研 —— 孤儿文件关联 / ProgID 的可判定性

> 调研人：Lead（原计划的调研成员多次中断，本文档由 Lead 实测完成）
> 日期：2026-10-25　|　性质：**只读调研，未改任何注册表（尤其未动 UserChoice）**
> 结论：**不做自动清理。能做且值得做的只有一件事：只读报告「指向已消失的第三方 exe」的关联，且必须过三层闸门。**

---

## 一、结论先行

文件关联比 CLSID **稍好**——链路短、每层都有明确的检查方法——但仍然过不了「误删 Windows 自有注册」这道关。

| 层面 | 结论 |
|---|---|
| 技术上能否找出断链 | **能**。本机 1285 个扩展名键，9.8 秒扫完，断链/可执行缺失仅 6 个（误报率可控） |
| 这 6 个是不是该删的垃圾 | **一半不是**。`.dic→txtfile`、`.shtml→shtmlfile`、`.wll→Word.Addin.8` 是 Windows/Office 自己的内置 ProgID（本机没有但系统按需注册），`.ocsmeet` 指向的 Office 是本机真实存在的软件 |
| 删除的风险 | **极高**。`UserChoice` 带防篡改 Hash；删 HKCR 侧可能让「打开方式」列表损坏；且 73% 的用户默认关联指向 MSIX 应用，普通权限根本读不到目标文件 |

一句话：**断链检测可行，自动清理不可行；能安全报告的范围只有「指向已消失的、非系统的、非 MSIX 的第三方 exe」，本机只有 1 条。**

## 二、关联链路

```
HKCR\.ext ──(默认值)──► ProgID ──shell\open\command──► "C:\…\app.exe" "%1"
   │                        │
   │ OpenWithProgids         └─CLSID──► HKCR\CLSID\{…}（COM 打开方式）
   ▼
HKCU\...\Explorer\FileExts\.ext\UserChoice ←【用户的实际选择，Windows 10 起带防篡改 Hash】
```

关键点：**真正生效的是 UserChoice**，HKCR 的默认值只是「候选之一」。
所以任何「清理孤儿关联」的动作如果只动 HKCR、不动 UserChoice，用户根本感知不到；
而动 UserChoice 是被 Windows 明确防着的（见 §四）。

## 三、真机实测

### 1. 规模与扫描成本

```
HKCR 扩展名键: 1285 个，全量扫完 9.8 秒
  无默认 ProgID 的:            511 个（正常形态，不等于孤儿）
  ProgID 正常:                 701 个
  ProgID 断链/可执行缺失:        6 个
```

扫描成本完全可接受——比 CLSID 那边好一个数量级（那边搜一个 GUID 要 16 秒）。

### 2. 那 6 条「断链」逐条验尸（这是核心数据）

| 扩展名 | 指向 | 验尸结论 |
|---|---|---|
| `.apk` | `MuMuPlayer.apk`（键不存在） | 第三方模拟器残留，**真孤儿** |
| `.psdc` | `Photoshop.CPSDFile.170`（键不存在） | Photoshop 升级后旧版本号 ProgID 残留，**真孤儿（升级残留）** |
| `.dic` | `txtfile`（键不存在） | **Windows 内置 ProgID**，本机 HKCR 没有但系统按需注册——删不得 |
| `.shtml` | `shtmlfile`（键不存在） | 同上，Windows 内置 |
| `.wll` | `Word.Addin.8`（键不存在） | **Office 内置 ProgID**，随 Office 按需注册——删不得 |
| `.ocsmeet` | `ocsmeet_auto_file` → `...\lync.exe` | lync.exe 路径断了，但属于**本机已装的 Office**（升级残留） |

**6 条里只有 1 条是干净的第三方残留。** 与 CLSID 那边的结论完全一致：
断链容易找，「可以安全删除」的判定不可靠——
Windows / Office / MSIX 的按需注册让「键不存在」不等于「没用了」。

### 3. UserChoice 专项（最大的坑）

```
FileExts 下扩展名: 558 个，有 UserChoice 的: 131（其中 116 个带 Hash）
UserChoice 指向: 126 个 → AppX（MSIX）92 个、经典 ProgID 34 个
AppX 形态的 ProgId 在 HKCR 里不存在（抽样 3/3 全部 False）
经典 ProgID 里指向不存在键的: 3 个（.oxps/.xps → Windows.XPSReachViewer，.wsb → Windows.Sandbox）
```

三个必须写下来的事实：

1. **UserChoice 带 Hash**（131 个里 116 个有值）。这个 Hash 由 Windows 用未公开算法生成，
   用于检测第三方篡改——本工具**读没问题，写等于和系统对抗**，改完轻则被系统还原，重则「打开方式」列表损坏。
2. **73% 的用户默认关联指向 MSIX**（92/126），而 `AppX*` 形态的 ProgId 在 HKCR 里不存在是**正常现象**
   （它们由 `ActivatableClasses` / 包清单解析）。任何以「HKCR 里找不到 = 孤儿」为判据的实现，
   会把用户设置的默认应用全部判成垃圾。
3. 剩下 3 个「断链」的（`Windows.XPSReachViewer` 等）是 **Windows 功能组件**，
   对应功能（XPS 查看器、Windows 沙盒）未启用时键就是不在的——用户哪天启用功能，键会回来。

## 四、删除的真实风险

| 动作 | 后果 |
|---|---|
| 删 HKCR 的 ProgID 键 | 该扩展名的「打开方式」列表里这一项消失；若它同时被多个扩展名引用则全部消失。可还原（.reg 备份），但用户得先发现坏了 |
| 删 `.ext` 的默认值 | 双击该类型文件时系统弹出「你要如何打开这个文件」——不算灾难，但体验破坏 |
| 写/删 `UserChoice` | **与系统防篡改机制对抗**。Hash 校验失败时 Windows 会忽略或重置；第三方工具写它的行为在 Windows 10 1809+ 被明确收紧 |
| 删 Windows/Office 内置 ProgID | 当下没症状（键本来就不在），用户启用对应功能或修复 Office 后，关联行为异常且难以排查 |

## 五、如果做：最小安全边界

只做**只读报告**，报告条件同时满足全部五条（本机实测命中 1 条：`.apk`）：

1. `UserChoice` 与 `OpenWithProgids` 里**都没有**任何活引用；
2. ProgID 键不存在，**或** command 指向绝对路径且文件确实不存在（裸文件名/相对路径一律跳过——CLSID 那边 705 个误判的教训）；
3. ProgID 名称与目标 exe 都**不是** `Windows.*` / `AppX*` / Office 内置形态；
4. 目标 exe 不在 `C:\Windows` 下、不带系统签名；
5. 不碰 `UserChoice`，只读。

## 六、建议

1. **不做自动清理**。收益（本机 1 条）与风险（UserChoice 防篡改、Windows 按需注册、MSIX 解析特性）完全不成比例。
2. 「只读报告」可以并入 v0.5 的残留报告页（与 CLSID 报告同页），让用户自己决定；实现成本约等于本文档 §三.1 的扫描逻辑。
3. v0.5 的主力方向仍是技术设计文档 §14.6 里已验证可判定的两项：服务 `ImagePath` 孤儿、文件与注册表状态不一致检测。
