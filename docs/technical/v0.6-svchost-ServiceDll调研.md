# v0.6 调研 —— svchost 宿主里的 ServiceDll 孤儿

> 调研人：Lead　|　日期：2026-10-25　|　性质：只读
> 结论：**判定可行，本机收益为零**。v0.6 不做，理由如下。

## 实测（Windows 11 22631）

| 项 | 数量 |
|---|---|
| ImagePath 含 svchost.exe 的服务 | 248 |
| 其中有 `Parameters\ServiceDll` 的 | 220 |
| ServiceDll 指向文件缺失 | **0** |
| 无 `Parameters\ServiceDll` 的 | 28 |

## 28 个无 ServiceDll 的不是孤儿

它们全是 Windows 的**按用户实例化服务**（`AarSvc_6bac4`、`CDPUserSvc_6bac4`、
`cbdhsvc_6bac4`、`ConsentUxUserSvc_6bac4` 等，名字带用户会话后缀），
它们的 ServiceDll 定义在**模板键**（不带后缀的同名键）里。判定时必须：
找到对应模板键的 `Parameters\ServiceDll`，否则会把系统服务误判成孤儿。

## 判定方法（如果将来做）

1. `ImagePath` 含 `svchost.exe` → 走宿主分支；
2. `Parameters\ServiceDll` 存在 → 展开后查文件存在性（绝对路径才查，同 CLSID 调研的裸文件名教训）；
3. `ServiceDll` 缺失 → 找同名模板键（去掉 `_xxxx` 会话后缀）的 ServiceDll，仍缺失才算孤儿；
4. ServiceDll 指向 System32 一律跳过（ADR-049 的权限陷阱教训）。

## 为什么 v0.6 不做

本机 248 个宿主、0 个孤儿。没有样本意味着：写出来的代码没有真实回归防护，
而 svchost 服务表全是系统组件——误删一个的代价远高于收益。与 CLSID 调研同一结论：
**判据能做，但收益为零时不应进入实现**。

若将来要做，复用本节的判定方法即可（判定本身不复杂，复杂的是确认不会误伤）。
