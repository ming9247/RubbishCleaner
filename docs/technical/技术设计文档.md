## 0. 文档目的与范围

本文档把产品文档中的**目标**翻译成**可执行的技术方案**：模块边界、类与接口签名、数据模型、算法、异常与降级策略、测试与构建方式。

覆盖范围：

- v0.1 MVP：自启动检测 + 进程可见性判定 + 流氓评分 + 绝对确认表 + WPF 基础 UI + UAC 提权
- v0.2 / v0.3 / v0.4 的接口预留与技术预研（卸载、MFT 残留扫描、注册表清理）

不在本文档范围：市场分析、UI 视觉稿、在线特征库服务端设计。

### 0.1 术语表

| 术语 | 含义 |
|------|------|
| 启动项（StartupEntry） | 一个具体的自启动点位记录，例如某个 Run 键值、某个启动文件夹快捷方式 |
| 程序画像（SoftwareProfile） | 以可执行文件为单位聚合后的"一个软件"，是评分与展示的最小单元 |
| 进程事实（ProcessFacts） | 运行期采集的客观信息：是否有可见窗口、是否在任务栏、签名状态等 |
| 确认表（Trust Table） | 白名单 + 黑名单组成的硬判定兜底表 |
| 降级（Degrade） | 数据源因权限/异常不可用时，记录告警并继续，而不是整体失败 |

## 1. 架构总览

### 1.1 分层与依赖规则

```
┌──────────────────────────────────────────────────────────┐
│ RubbishCleaner.App   (net8.0-windows, WPF)               │
│  View (XAML) → ViewModel (MVVM) → 调用 Core 用例           │
└───────────────────────┬──────────────────────────────────┘
                        │ 只能向下依赖
┌───────────────────────▼──────────────────────────────────┐
│ RubbishCleaner.Core  (net8.0, 无 UI 依赖)                 │
│  Detection / Scoring / Trust / Models / Abstractions      │
└───────────────────────┬──────────────────────────────────┘
                        │
┌───────────────────────▼──────────────────────────────────┐
│ RubbishCleaner.Common (net8.0, 无业务逻辑)                 │
│  Win32 P/Invoke / 注册表 / 签名 / 快捷方式 / 日志 / 提权     │
└──────────────────────────────────────────────────────────┘
```

**硬性规则（Code Review 检查项）**：

1. `Core` 与 `Common` **不得**引用 `System.Windows.*`、`PresentationFramework`。所有 UI 无关逻辑必须可在单元测试中以控制台方式运行。
2. `Common` 只放"操作系统能力封装"，**不得**包含评分、判定等业务规则。
3. `App` 不得直接 P/Invoke，所有系统访问经由 `Core`/`Common` 的接口。
4. 所有外部副作用（注册表、文件、进程、WMI/COM）必须藏在接口之后，便于测试注入。

### 1.2 为什么这样分层

| 关注点 | 落地方式 |
|--------|---------|
| 可测试性 | 检测源、签名校验、进程事实采集全部接口化，测试中用假实现替代真实系统 |
| 误报可追责 | 每条结论都带 `Evidence`（证据链），UI 可展示"为什么判它为高风险" |
| 未来 CLI 化 | Core 不依赖 WPF，后续可加 `RubbishCleaner.Cli` 复用全部逻辑 |
| 权限隔离 | 提权只发生在 App 进程，Core 通过接口感知 `IsElevated` 并降级 |

## 3. 核心数据模型

### 3.1 StartupEntry —— 单个自启动点位

```csharp
public sealed class StartupEntry
{
    public required string Id { get; init; }            // 稳定标识：SHA1(Source|Location|Name)
    public required StartupSourceKind Source { get; init; }
    public required string Name { get; init; }          // 值名 / 快捷方式名 / 服务名 / 任务名
    public required string Location { get; init; }      // 注册表全路径或文件夹路径
    public string? RawCommand { get; init; }            // 原始命令行
    public string? ExecutablePath { get; init; }        // 解析出的可执行文件绝对路径
    public string? Arguments { get; init; }

    public bool IsSigned { get; init; }
```

## 4. 检测引擎设计

### 4.1 扫描流水线

```
 [1] 数据源枚举（并行）          IStartupSource.CollectAsync()
        │  Run(3) / StartupFolder(2) / Service / ScheduledTask
        ▼
 [2] 命令行 → 可执行路径归一化    CommandLineResolver.Resolve()
        │  去引号 / 取首段 / 处理 rundll32、svchost、explorer
        ▼
 [3] 去重（Source+Name+Command）  并合并同 exe 的多条启动项
        ▼
 [4] 进程事实采集                 IProcessFactsProvider.GetFacts(exePath)
        │  EnumWindows / 签名校验（按路径缓存）
        ▼
 [5] 快捷方式存在性探测            Desktop / StartMenu 目录索引一次，O(1) 查询
        ▼
 [6] 确认表匹配                   TrustTable.Match()  → Safe / Malicious / Unknown
        ▼
 [7] 评分                        RiskScorer.Score(profile)
        ▼
 [8] 排序输出                    高风险 → 疑似 → 正常；同级按名称
```

设计要点：

- **第 1 步并行、第 4 步并行**：注册表读取与签名校验是主要耗时点；使用 `Task.WhenAll` + `Parallel.ForEachAsync`（限制并发度 = CPU 核数，避免签名校验的 COM 争用）。
- **每步都可取消**：全链路传递 `CancellationToken`，UI 的"停止扫描"按钮立即生效。
- **失败隔离**：任一数据源抛异常 → 该源标记为 `Degraded`，其余继续；不抛出到 UI 线程。

### 4.2 数据源接口

```csharp
public interface IStartupSource
```

### 4.3 各数据源实现要点

| 数据源 | 读取方式 | 权限 | 失败降级策略 |
|--------|---------|------|-------------|
| RegistryRun（HKCU/HKLM/WOW64） | `RegistryKey.OpenBaseKey` + `GetValueNames`；值类型 `REG_SZ`/`REG_EXPAND_SZ` 都需展开 `%VAR%` | HKCU 免提权；HKLM 读取一般免提权 | 键不存在 → 空结果（非错误）；`SecurityException` → Degraded |
| StartupFolder | `Directory.EnumerateFiles("*.lnk")` + `IShellLink` 解析目标路径 | 免提权 | 目录不存在 → 空；单文件解析失败 → 该条 `IsReadable=false` |
| WindowsService | 读 `HKLM\SYSTEM\CurrentControlSet\Services` 子键，筛选 `Start==2`（自动）+ `Type` 含 `SERVICE_WIN32`；**排除**微软签名的服务 | 读取一般免提权（部分子键拒绝访问需跳过） | 单键拒绝访问 → 跳过并计数；整体失败 → Degraded |
| ScheduledTask | 优先用 `Microsoft.Win32.TaskScheduler` 风格的 COM 互操作，v0.1 采用**目录枚举 + XML 解析**（`C:\Windows\System32\Tasks`），避免引入第三方包 | 需管理员（部分任务 ACL 限制） | 无权限 → Degraded，UI 提示"以管理员身份运行可获取完整计划任务" |

> **为什么计划任务不用 COM**：`TaskScheduler` COM 需要额外 NuGet 包（`TaskScheduler` 2.11+），与"轻量绿色单文件"目标冲突；且 COM 在无管理员权限时同样会失败。v0.1 用 `Tasks` 目录 XML 解析即可拿到 `Command`/`Arguments`，覆盖绝大多数流氓软件场景。v0.2 若需触发器细节（如"登录时"vs"每天"）再引入 COM。

### 4.4 命令行解析规则（`CommandLineResolver`）

按顺序尝试，命中即返回：

1. **`explorer.exe` + `shell:` 协议**：如 `explorer.exe shell:startup` → 视为文件夹引用，不产生可执行路径。
2. **`rundll32.exe`**：取第一个参数 DLL 路径作为归属文件（`rundll32 "C:\x\a.dll",Entry` → `C:\x\a.dll`）。
3. **`svchost.exe -k`**：归属到服务宿主，不解析为独立程序（避免把 `svchost` 全盘判为可疑）。
4. **`cmd.exe /c ...`**：提取 `/c` 之后的第一个可执行 token。
5. **引号包裹**：`"C:\Program Files\A\a.exe" -arg` → `C:\Program Files\A\a.exe`。
6. **无引号含空格**：从最长可行前缀向前回溯，找到第一个真实存在的 `.exe` 文件（`File.Exists`）；找不到则取第一个空白前的 token。
7. **环境变量**：解析前先 `Environment.ExpandEnvironmentVariables`。
8. **相对路径**：相对当前工作目录不可靠，标记 `ExecutablePath=null` 并保留 `RawCommand`。

**安全边界**：解析只做字符串与 `File.Exists` 判断，**不执行**任何命令。

### 4.5 可见性与任务栏判定算法

```csharp
// 1) 一次性枚举所有可见顶层窗口，建立 pid → (count, hasTaskbar) 映射
EnumWindows((hwnd, _) =>
{
    if (!IsWindowVisible(hwnd)) return true;
    if (GetWindowTextLength(hwnd) == 0) return true;
    GetWindowThreadProcessId(hwnd, out uint pid);
    var exStyle = GetWindowLongPtr(hwnd, GWL_EXSTYLE);
    bool toolWindow = (exStyle & WS_EX_TOOLWINDOW) != 0;
    bool hasOwner   = GetWindow(hwnd, GW_OWNER) != IntPtr.Zero;
    bool hasAppWindow = (exStyle & WS_EX_APPWINDOW) != 0;
    bool taskbar = hasAppWindow || (!toolWindow && !hasOwner);
    map.Add(pid, taskbar);
    return true;
});
```

- **性能**：全量枚举一次（通常 < 500 个窗口），再按 pid 查表，避免"每个进程枚举一遍窗口"的 O(n²)。
- **托盘图标**：不实现（无公开 API）。产品文档已明确降级为"疑似加分项"；v0.1 直接**不加分也不减分**，在 `Evidence` 中标注 `TRAY_UNKNOWN`，UI 以灰色说明"无法判定"。
- **UWP/打包应用**：`ApplicationFrameHost` 承载，窗口归属 pid 与真实进程不同。v0.1 对 `ApplicationFrameHost` 进程名直接跳过可见性判定（视为有窗口），防止误判。

### 4.6 签名校验

> ⚠️ **本节在原设计基础上做了修正（ADR-006 已推翻）**，原因见下方"目录签名陷阱"。

采用**两级校验**，按成本从低到高：

1. **内嵌签名**：`X509Certificate.CreateFromSignedFile(path)`。能直接读到证书主体，信息最完整。
2. **目录签名（catalog）**：`WinVerifyTrust` + `CryptCATAdminAcquireContext2` / `CryptCATAdminCalcHashFromFileHandle2` / `CryptCATAdminEnumCatalogFromHash` / `CryptCATCatalogInfoFromContext`。

#### 4.6.1 为什么必须做第二级（目录签名陷阱）

Windows 自带的大量系统二进制**没有内嵌签名**，而是由 `%SystemRoot%\System32\CatRoot` 下的
安全目录（`.cat`）统一签名。实测：

```
C:\Windows\System32\spoolsv.exe        => NO EMBEDDED SIG   (Get-AuthenticodeSignature: Valid)
C:\Windows\System32\SearchIndexer.exe  => NO EMBEDDED SIG   (Get-AuthenticodeSignature: Valid)
C:\Windows\System32\svchost.exe        => EMBEDDED: CN=Microsoft Windows Publisher, O=Microsoft Corporation
```

如果只用 `CreateFromSignedFile`，会把 `spoolsv`、`SearchIndexer` 等判成"未签名"，
再叠加"无窗口/无图标"就直接推成**高风险**——这正是首次真机扫描时出现的问题（26 项疑似里大量是微软服务）。

#### 4.6.2 判定"微软签名"

- 内嵌签名：Subject 含 `O=Microsoft Corporation` 或 `CN=Microsoft Windows`。
- 目录签名：**无法取到证书主体**，因此改用"文件是否位于 `%SystemRoot%` 下"作为保守近似。
  非系统目录的文件即使有目录签名，也不会被当成微软——宁可少判白，不可错判白。

#### 4.6.3 实现要点与踩坑

```csharp
var catalogTrustInfo = new WinTrustCatalogInfo {
    pcwszCatalogFilePath  = catalogPathPtr,
    pcwszMemberTag        = memberTagPtr,      // 文件哈希的十六进制大写
    pcwszMemberFilePath   = memberPathPtr,
    hMemberFile           = hFile,             // 传已打开的句柄，避免重复打开
    pbCalculatedFileHash  = hashPtr,
    cbCalculatedFileHash  = hashLength,
    pcCatalogContext      = IntPtr.Zero,       // ← 必须 NULL，否则 AccessViolation
    hCatAdmin             = catAdmin,
};
```

> **坑**：`pcCatalogContext` 类型是 `PCATALOG_INFO`，`WinVerifyTrust` 会把它当结构体指针解引用。
> 传枚举句柄或 `CATALOG_INFO` 指针都会直接 `AccessViolationException` 让进程崩溃。
> 正确值是 **`NULL`**。

#### 4.6.4 性能

以 exe 路径为 key 做 `ConcurrentDictionary` 缓存，同一路径只校验一次。
目录签名比内嵌签名慢（要算哈希 + 查目录），但只有内嵌签名缺失时才走，实测总耗时从 3116 ms 降到 420 ms。

#### 4.6.5 已知限制

不做吊销检查（`WTD_REVOKE_NONE`）：离线场景下吊销检查会显著拖慢扫描。v0.2 再评估。

## 5. 评分与绝对确认表

### 5.1 评分模型

> ⚠️ **实现时新增了"不适用（NotApplicable）"语义**，这是原设计的缺口，见 5.1.3。

| 规则 ID | 特征 | 权重 | 判定来源 |
|---------|------|------|---------|
| `AUTOSTART` | 存在任意自启动项 | +30 | 启动项集合非空 |
| `NO_VISIBLE_WINDOW` | 运行中且无可见窗口 | +25 | `ProcessFacts.HasVisibleWindow == false` |
| `NO_DESKTOP_ICON` | 桌面无对应快捷方式 | +15 | 桌面目录索引 |
| `NO_START_MENU` | 开始菜单无对应快捷方式 | +15 | 开始菜单索引 |
| `NO_TRAY` | 无托盘图标 | +15 | **v0.1 不启用**（无可靠 API），标记为"不适用" |
| `UNSIGNED` | 无签名或发行商未知 | +10 | 签名校验（含目录签名） |
| `MASQUERADE` | 进程名伪装系统名 | +10 | 与系统进程名编辑距离 ≤1 且非系统路径 |
| `ORPHAN_STARTUP` | 启动项指向的文件已不存在 | **0** | `File.Exists(ExecutablePath)` 为 false（v0.1.2 新增） |

#### 5.1.0 失效启动项（v0.1.2 新增）

**现象**：真机上发现某软件（WorkBuddy 国内版）换目录安装后，注册表里留下了
两条指向旧路径的 Run 项，两条路径都已不存在。原实现会因为
"无桌面图标 + 无开始菜单 + 未签名"把它算成 **70 分疑似**。

这是错的：程序根本不存在，"未签名""无窗口""无图标"全都是**伪信号**。
它真正的问题是"该清理的残留"，而不是"可疑的流氓软件"。

**处理**：

1. `StartupEntry.TargetExists` 判定目标文件是否存在。为 false 时 `IsOrphan = true`。
2. `SoftwareProfile.IsOrphaned` = 所有启动点都失效；`OrphanEntries` 给出具体名单（支持部分失效）。
3. 失效记录的 `NO_VISIBLE_WINDOW` / `NO_DESKTOP_ICON` / `NO_START_MENU` / `UNSIGNED`
   全部标记为 **不适用**，只剩 `AUTOSTART` 计 30 分 → 归为**正常**，不制造噪声。
4. `ORPHAN_STARTUP` 权重为 **0**：它不是风险，是待办事项。
   保留这条规则是为了让 UI 与报告能明确说"这条该清理"。
5. UI 增加「清理 / 残留启动项（N）」分组，一键筛出所有失效项。

**判定边界（很重要）**：只有**绝对路径**才判失效。
计划任务与服务的命令行常写成裸文件名（如 `BthUdTask.exe`），由系统按 System32 解析；
若把这类相对路径也判为"不存在"，会把大量正规系统任务误报成残留。

实测效果：该机器上识别出 3 条失效启动项，
`WorkBuddy` 两条从 70 分"疑似"降为 30 分"正常 + 残留"，并额外发现 `WsxService` 的服务残留。

> **测试可注入性**：`StartupEntry.TargetExistsOverride` 允许测试显式指定"存在/不存在"，
> 避免评分与排序的单元测试被迫依赖真实文件系统。

#### 5.1.1 伪装判定细则

内置系统进程名集合（`svchost`、`lsass`、`csrss`、`winlogon`、`services`、`explorer`、`smss`、`wininit`、`spoolsv`、`taskhostw`…），若进程名与之**编辑距离 ≤ 1** 且不等于原名 → 命中。

**距离算法用 Damerau-Levenshtein（受限最优字符串对齐 OSA），不是普通 Levenshtein。**
原因：`scvhost` 是 `svchost` 的相邻字符换位，普通 Levenshtein 算出来是 2（两次替换），
而换位恰恰是最常见的仿冒手法之一。Damerau 把换位记为 1，才能覆盖这一类。

#### 5.1.2 公式

```
raw   = Σ weight(rule) for (rule.Hit && !rule.NotApplicable)
total = clamp(raw, 0, 100)
```

**分级**：`0–40 Normal` / `41–70 Suspicious` / `71–100 HighRisk`。

#### 5.1.3 "不适用"语义（实现中补上的关键设计）

最初版本只有 `Hit`（命中/未命中）两种状态，真机扫描时暴露出两个问题：

**问题 A：未运行的进程被算作"已排除嫌疑"。**
`NO_VISIBLE_WINDOW` 需要进程运行才能判定。若进程没运行就记 `Hit=false`，
在 UI 上会显示成"这条规则检查过了、没问题"，这是误导。

**问题 B：正规服务被判高风险。**
NVIDIA `nvcontainer`、Intel `esrv_svc` 等只通过 Windows 服务自启动。
服务**按设计**就没有窗口、桌面图标、开始菜单入口，三条规则合计 +55，
叠加自启动 +30 直接到 85 分 → 高风险。这是纯误报。

**解决方案**：给 `ScoreItem` 增加 `NotApplicable` 标记。

```csharp
public sealed record ScoreItem(
    string RuleId, string Description, int Weight, bool Hit, bool NotApplicable = false)
{
    // 关键：不适用项一律不计分，即使 Hit 为 true
    public int Contribution => Hit && !NotApplicable ? Weight : 0;
}

public sealed record RiskScore(...)
{
    public int HitCount  => Items.Count(i => i.Hit && !i.NotApplicable);
    public int RuleCount => Items.Count(i => !i.NotApplicable);   // 分母也排除
}
```

标记为不适用的三种情况：

| 情况 | 涉及的规则 |
|------|-----------|
| 进程未运行 | `NO_VISIBLE_WINDOW` |
| 纯服务型程序（`SoftwareProfile.IsServiceOnly`） | `NO_VISIBLE_WINDOW`、`NO_DESKTOP_ICON`、`NO_START_MENU` |
| 无可靠 API | `NO_TRAY` |

> **踩坑记录**：第一次只加了标记、没改 `Contribution`，分数纹丝不动（仍然 85）。
> 教训：加语义标记时，必须同时审计所有消费该标记的地方。

**修复后的实际效果**（同一台机器）：

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| 高风险 | 2（含 NVIDIA 误报） | 1 |
| 疑似 | 26（大量正规厂商服务） | 11 |
| 正常 | 23 | 37 |

**白名单压制**：`Trust == Safe` 时强制 `Level = Normal`（保留原始分数用于展示，标记 `Suppressed=true`），避免"微软签名的后台服务"被判高风险。

### 5.2 确认表（Trust Table）

#### 5.2.1 文件位置与加载顺序

1. `%ProgramData%\RubbishCleaner\trust-table.json`（用户自定义，优先级最高，可覆盖内置）
2. 程序目录 `Resources\trust-table.json`（随版本分发）
3. 内置硬编码兜底（编译进程序，防止文件缺失导致误判）

合并策略：**用户表整体覆盖内置表的同名分类**（简单可预期），而非逐条合并。

#### 5.2.2 JSON Schema

```jsonc
{
  "version": 1,
  "updated": "2026-10-23",
  "whitelist": [
    { "type": "signer",  "value": "Microsoft Corporation", "note": "微软签名" },
    { "type": "signer",  "value": "Tencent Technology" },
    { "type": "path",    "value": "%SystemRoot%\\System32\\", "note": "系统目录" },
    { "type": "sha256",  "value": "ab12...", "note": "精确到文件哈希" },
    { "type": "name",    "value": "ctfmon", "note": "进程名（不含扩展名）" }
  ],
  "blacklist": [
    { "type": "namePattern", "value": "*.流氓*" },
    { "type": "namePattern", "value": "hao123*" },
    { "type": "path",        "value": "%LocalAppData%\\Temp\\" },
    { "type": "signer",      "value": "Some Known Bad Vendor" }
  ]
}
```

规则类型语义：

| type | 匹配对象 | 匹配方式 |
|------|---------|---------|
| `signer` | 签名 Subject | 不区分大小写 `Contains` |
| `path` | 可执行文件完整路径 | 展开环境变量后**前缀匹配**（目录须以 `\` 结尾） |
| `sha256` | 文件哈希 | 精确匹配（惰性计算，仅当规则存在时才算） |
| `name` | 进程名（无扩展名） | 不区分大小写精确匹配 |
| `namePattern` | 进程名或文件名 | 通配符（`*`/`?`），转为正则 |

#### 5.2.3 判定优先级（决策记录 ADR-001）

产品文档写"白名单命中 → 安全；黑名单命中 → 高风险"，未定义两者同时命中的情形。

**本项目决策：黑名单优先。** 理由：白名单中 `path` 规则可能覆盖整个目录（如 `%LocalAppData%\Temp\`），若白名单优先，攻击者把程序放到 Temp 即可"洗白"。黑名单优先符合"宁可提示、不可漏判"的安全取向，且误报的代价（用户看到黄色提示）远低于漏报。

```
if (blacklist.Match()) → Malicious  (Level 强制 HighRisk)
else if (whitelist.Match()) → Safe  (Level 强制 Normal)
else → Unknown → 走启发式评分
```

#### 5.2.4 内置黑名单的合规约束

内置表**只收录公开可查的 PUP/PUA 特征**（进程名模式、路径特征），不针对具体企业做主观定性；用户可自行编辑 `%ProgramData%` 下的表。这是产品合规声明（"仅检测与协助，不做静默删除"）的技术落地。

### 5.3 误杀防护三道闸

1. **确认表白名单**：微软签名 / 系统目录直接压制。
2. **分级呈现**：默认只展示、不自动处置；高风险项也需要用户逐条确认。
3. **证据可见**：每一项都显示命中了哪几条规则，用户可自行判断（例如"无桌面图标"对服务型软件是正常的）。

## 8. 异常处理与日志

### 8.1 原则

- **数据源级隔离**：单个源失败不影响整体，结果里带 `Degraded` 标记。
- **UI 线程零异常**：所有异步命令用 `try/catch` 包裹，异常转为状态栏消息 + 日志。
- **全局兜底**：`App.xaml.cs` 挂 `DispatcherUnhandledException`、`AppDomain.UnhandledException`、`TaskScheduler.UnobservedTaskException`，写日志后提示用户，不静默崩溃。

### 8.2 日志

- 位置：`%LocalAppData%\RubbishCleaner\logs\app-yyyyMMdd.log`
- 级别：`INFO / WARN / ERROR`，带时间戳与线程 ID
- 滚动：按天分文件，保留 7 天，单文件超 5MB 截断
- **不记录**用户文件内容，只记录路径与判定结果（隐私）
- 提供"打开日志目录"入口，便于用户反馈问题

## 12. 后续版本技术预研

### 12.1 v0.2 卸载引擎（已实现）

#### 12.1.1 软件列表：枚举与过滤

数据源三处：`HKLM` 64 位、`HKLM\WOW6432Node`、`HKCU` 的 `...\CurrentVersion\Uninstall`。

**实测数据（本机）**：520 个原始条目里只有 **114 个是真正可展示的软件**。过滤掉 406 个，规则如下：

| 过滤条件 | 本机数量 | 理由 |
|---------|---------|------|
| `SystemComponent=1` | 376 | 系统补丁/运行库/组件，不是"用户装的软件" |
| 无 `DisplayName` | — | 没有名字无法展示 |
| 无 `UninstallString` | 116 | 对卸载工具无意义 |
| `NoRemove=1` / `ParentKeyName` 非空 | 62 | 明确不可卸载 / 是子组件 |

不过滤的话，114 个真软件会被淹没在 400 多个系统组件里，工具直接不可用。

#### 12.1.2 脏数据清洗（真实踩到的坑）

实测本机「明日之后」条目，`DisplayName`、`Publisher`、`UninstallString` **全部被污染**：

```
DisplayName : 明日之后 羮翶 琢 Ѐ 琢 Ѐ 쳐恓ǹ 翻 …
Publisher   : 杭州网易雷火科技有限公司 a  耀 UninstallString  退䌀恑ǹ …
```

第三方安装器把二进制垃圾直接写进了注册表字符串。

`RegistryTextSanitizer` 的策略是**截断到第一个可疑字符**，而不是"过滤掉非法字符"：
垃圾通常从某处开始整段污染，后面的内容没有保留价值，而前面的部分（如「明日之后」）
恰恰是有效信息。

可疑字符判定：控制字符、私用区（U+E000–U+F8FF）、孤立代理项、零宽空格。

#### 12.1.3 卸载前三道检查

卸载要执行来自注册表的命令，而注册表<b>可以被任何程序写入</b>，必须当作不可信输入。

| 检查 | 拒绝条件 | 防护目标 |
|------|---------|---------|
| 命令存在性 | 无 `UninstallString` | 没有命令无从执行 |
| 系统工具拦截 | 主程序是 `cmd`/`powershell`/`reg`/`sc`/`mshta` 等 | 防注册表被篡改后借本工具执行任意命令 |
| 程序存在性 | 卸载器文件不存在 | 用户手动删过目录的常见情况，给出"用清理残留"的指引 |

**rundll32 的有条件例外**（实测踩过）：NVIDIA 全家桶 7 个组件的官方卸载命令是
`RunDll32.EXE "…\NVI2.DLL",UninstallPackage Display.Driver`。
第一版被"禁止系统工具"规则一刀切拦下，属于误杀。

判定要点：**rundll32 本身不可疑，可疑的是"加载任意 DLL"**。放行条件：

1. DLL 是绝对路径；
2. DLL 文件真实存在；
3. DLL **不在系统目录**（系统目录的 DLL 不该被第三方软件当卸载器）。

> 后续验证发现：本机这 7 条 NVIDIA 的 `InstallerCore` 目录**已经不存在**，
> 所以它们仍然被拦截——**这是正确行为**，它们是卸载器已失效的残留条目。
> 借此在列表里加了"卸载程序缺失"标记，而不是让用户点了才发现。

#### 12.1.4 执行策略：薄封装

`UninstallExecutor` 刻意保持"薄"——只负责"启动进程、等待、报告"：

- **不自行拼接静默参数**：各软件静默参数五花八门（`/S`、`/silent`、`/qn`、`--silent`），
  猜错会导致卸载异常甚至卡死。要用静默就用注册表里现成的 `QuietUninstallString`。
- **用 `ShellExecute`**：很多卸载器清单里要求管理员，需要它自己触发 UAC。
- **15 分钟超时**：大型软件（Adobe 系）卸载耗时很长，但也不能无限等。
- **不做任何强制删除**：卸载由软件自己的安装器负责，这是产品合规底线。

#### 12.1.5 检查顺序的重要性

踩过的坑：先把"系统工具拦截"放在"绝对路径校验"之后，结果 `cmd.exe /c ...`
报的是"不是绝对路径"，掩盖了真正原因（指向系统工具），提示信息会误导用户。

**安全拦截必须最先执行。**

|------|-----------|

### 12.2 v0.3 残留扫描（已实现）

#### 12.2.1 为什么"按名字猜残留"这条路走不通

行业常见做法是"目录名像某个已卸载软件 → 判为残留"。本机实测这条路<b>不可用</b>：

| 口径 | 本机命中 | 说明 |
|------|---------|------|
| 5 个常见根目录（Program Files / Program Files (x86) / ProgramData / LocalAppData / Roaming）的顶层目录 | **306 个** | 候选池 |
| 名字能对上已安装软件（含包含关系） | **21 个** | 高置信度"有主" |
| 名字对不上的 | **285 个** | 若按名字判残留，误报率 ≈ 93% |

对不上的那 285 个里，绝大多数<b>确实属于已装软件</b>，只是名字对不上：

```
C:\Program Files\NVIDIA Corporation          # 驱动装在别处，这是共享数据目录
C:\Users\taco\AppData\Local\ASP.NET          # .NET 运行时的公共缓存
C:\Users\taco\AppData\Roaming\Code           # VS Code 的用户数据
C:\Users\taco\AppData\Roaming\Tencent        # 厂商根，下面挂着 QQNT / WeChat / QQLive
C:\ProgramData\Intel Package Cache {GUID}    # 安装器缓存
```

结论：**名字匹配只能用于"证明有主"（避免误报），不能用于"证明是残留"（会大量误报）。**

#### 12.2.2 判定依据：只信硬痕迹

v0.3 只用两类硬证据判定残留：

| 类型 | 判据 | 置信度 | 为什么可信 |
|------|------|--------|-----------|
| `OrphanedUninstallerDirectory` | 目录里还留着卸载程序（`unins000.exe` / `uninst.exe` / `uninstall.exe` 等），且**没有任何已安装软件认领该目录** | 高 | 卸载程序的存在本身就证明"这里装过软件"；无人认领证明它已被卸载 |
| `StartupTrailDirectory` | 失效启动项指向的文件已不存在，**但它所在目录仍然存在**，且无人认领 | 高 | 启动项是"装过东西"的铁证，文件没了而目录还在 = 软件被删、目录留下 |
| `NameMatchedDirectory` | 仅名字相似 | 低 | 默认不进清理计划，只作提示（当前版本不产出此类，预留给后续特征库） |

**"认领"的定义**（`LeftoverScanner.BuildClaims`）——三条来源：

1. `InstallLocation`；
2. 卸载程序所在目录；
3. 卸载程序所在目录的**上一级**（很多软件注册表只写了产品目录，实际装在 `Vendor\Product`）。

匹配是**双向**的：目录位于认领路径之下算有主；目录<b>包含</b>认领路径也算有主。
第二条是实测逼出来的——本机 `C:\Program Files\OEM` 下有孤儿卸载程序，但
`C:\Program Files\OEM\机械革命电竞控制台` 是**在用的已装软件**：
只做单向匹配会把父目录报成残留，一删就把在用的软件连带删掉。

> ⚠️ **两个必须做对的过滤器**（都是真机 E2E 里踩出来的）：
> - 认领路径要求层级 ≥ 3 且末端不是 `Program Files` / `ProgramData` / `AppData` 这类**容器名**。
>   否则本机多个软件的卸载器直接躺在 `C:\Program Files\<Vendor>` 下，会把 `C:\Program Files`
>   也加进认领集合，于是**整棵树都"有主"，一条残留都报不出来**。
> - 认领证据必须包含**被过滤掉的**注册表条目（`SystemComponent=1`、无 `DisplayName`）。
>   本机 Adobe CoreSync 的条目没有 DisplayName，不展示，但它目录里的 `uninstall.exe`
>   如果只按"可展示软件"认领，就会被判成孤儿 → 真实误报。
>   因此 `InstalledAppEnumerator` 额外输出 `ClaimPaths`。

**厂商共享目录降级**：位于 `Common Files` / `Shared` / `ProgramData` 这类"共享容器"下、
且路径命中某个已装厂商名的，降为 Medium（只提示、不自动清理）。
本机实例：`Common Files\Autodesk Shared\AdskLicensing` 有 6 MB 的 `uninstall.exe`、
注册表里也没有对应条目，但它其实是 AutoCAD 授权组件在用的东西。
（刻意<b>不</b>对所有带厂商名的目录降级，否则 `Program Files\Tencent\QQOld` 这种真残留
也会被降成"只提示"，清理能力就没了。）

#### 12.2.3 文件索引：USN 直读 + 目录遍历回退

```
CreateFile("\\.\C:", GENERIC_READ, FILE_SHARE_READ|WRITE|DELETE, OPEN_EXISTING, FILE_FLAG_BACKUP_SEMANTICS)
  → DeviceIoControl(FSCTL_ENUM_USN_DATA)
  → 每条 USN_RECORD 给出 (FRN, 父FRN, 文件名, 文件属性)
  → 建 FRN→(父FRN,名字) 字典，路径靠父子链回溯
```

两套实现共用一个接口 `IVolumeFileIndex`，由 `CompositeVolumeFileIndex` 自动选择：

| 实现 | 权限 | 本机实测 | 用途 |
|------|------|---------|------|
| `UsnFileIndex` | **需管理员** | C: 82.3 万条 / 1.8–2.6 秒 / 峰值约 110 MB；D: 52.9 万条 / 2.5 秒 | 主路径 |
| `FallbackVolumeFileIndex` | 标准用户可用 | 同 5 个根目录约 3–20 秒 | 回退，结果一致 |

两套实现的结果做过交叉验证（同名集合逐个比对）：`C:\Windows`、`C:\Windows\System32`、
`C:\Program Files\Common Files` 均**缺失 0 / 多余 0**。

**实测踩到的坑**（都已写进代码注释）：

1. `HighUsn` 必须传 `long.MaxValue`（0x7FFF…FFFF）。传 `ulong.MaxValue` 会立刻返回
   `ERROR_HANDLE_EOF(38)` 且拿到 **0 条记录**——看起来像"权限不够"或"卷不支持"，其实只是参数写错。
2. 标准用户下 `CreateFile` 卷句柄返回 **err=5**（拒绝访问）。实测换成 `0`、`0x80`、`0x120089`
   等访问权限组合同样是 err=5，因此标准用户**不可能**用 USN，必须回退。
3. **根 FRN 不是 5**：`FileReferenceNumber` 是"高 16 位序号 + 低 48 位记录号"的打包值，
   根目录实测 `0x0005000000000005`。直接 `== 5` 判断会让父链永远到不了顶，
   每条记录都被当断链处理（症状：扫 `System32` 命中 0 条）。
4. **硬链接会漏报**：NTFS 硬链接是"一条 MFT 记录、多个目录项"，索引里只看到其中一个名字。
   实测 `System32\notepad.exe` 与 WinSxS 那份同属一个记录，只保留 WinSxS 的名字。
   已在命中文件上补 `FindFirstFileNameW` 展开全部链接名（注意该 API 会把第一个名字
   直接写进缓冲区，不能当"只探测长度"用）。
5. `UsnJournal` 被删除时 `FSCTL_ENUM_USN_DATA` **仍然可用**（它枚举 MFT 而不是日志），
   所以不需要先 `FSCTL_CREATE_USN_JOURNAL`。

**为什么不是完整 `$MFT` 解析**：Everything 方案要解析 NTFS 引导扇区、`$MFT` 的 `DATA` 运行列表、
属性头、压缩与稀疏标志，约 2000 行且极易在非常规卷上出错。
USN 枚举把这一切交给内核，2 秒量级的全盘枚举已经满足"轻量、用完即走"的产品定位。

#### 12.2.4 七道安全闸门

残留判定本质是启发式，无论证据多硬都存在误判。因此"能不能删"与"扫出什么"**彻底解耦**：
扫描器只管产出，`LeftoverSafetyGuard`（纯函数，可穷举单测）决定是否允许删除。

| # | 闸门 | 拒绝示例 |
|---|------|---------|
| 1 | 路径非空、可解析、**原始输入**是绝对路径 | `AppData\Local\Foo`（`Path.GetFullPath` 会静默补全成绝对路径，所以必须在补全前判断） |
| 2 | 不是盘根 | `C:\` |
| 3 | 层级足够（≥ 2 级） | `C:\Program Files` |
| 4 | 不在系统保护路径下 | `C:\Windows\SysWOW64\X`、`…\Common Files\Vendor`、`…\InstallShield Installation Information\{GUID}` |
| 5 | 不与系统保留名冲突 | `…\Microsoft`、`…\Package Cache`、`…\Temp` |
| 6 | 与本程序所在目录不重叠 | 删 `D:\Tools` 会连带删掉正在运行的自己 |
| 7 | 不是重解析点（符号链接 / 目录联接） | 删链接会牵连真实目标 |

**被拒的项依然展示给用户**（只是标记"不可自动清理"），而不是直接藏起来——
用户需要知道"这里还有残留，但工具不敢动"。

#### 12.2.5 清理：只移入回收站

`LeftoverCleaner.Execute` 只接受"移入回收站"这一种删除方式，代码里**不存在**
`File.Delete` / `Directory.Delete` 的兜底分支。理由：误判是必然的，
一次误删就是不可恢复的数据损失；放进回收站把误判成本从"永久"降为"右键还原"。

实现用 `SHFileOperationW`（`FOF_ALLOWUNDO`），四个必须踩准的细节：

1. `pFrom` 必须**双 null 结尾**（路径 + `\0` + `\0`），否则 shell 会读到缓冲区外的野内存。
2. 返回值是 win32/`DE_*` 码而**不是 HRESULT**，不能用 `Marshal.GetLastWin32Error` 顶替。
3. `fAnyOperationsAborted` 必须单独判——返回 0 也可能什么都没做。
4. `FOF_ALLOWUNDO` 只是"允许撤销"——在**没有回收站的卷**（网络盘 / 可移动盘）上
   shell 会静默降级成永久删除**且照样返回 0**。所以必须提前拒绝非 `DriveType.Fixed` 的卷。

清理同样保留"执行前重新校验"：扫描到点确认之间目录可能已被删除或换成别的东西。

**实测验证**（真机，非模拟）：造 4 文件 / 1310826 字节的样本 → 扫描命中 →
进回收站（`DeletedFrom` 指向原父目录、verbs 含"还原"）→ 还原后
`app.exe`=1048576 / `bin\lib.dll`=262144，**SHA256 与删除前完全一致**。
标准权限与提权两种模式下均验证通过。

### 12.4 v0.3.1 卸载与残留联动（已实现）

#### 12.4.1 为什么需要这一版

v0.3.0 的通用扫描是**启发式**的：它不知道用户卸过什么，只能靠"孤儿卸载程序 / 失效启动项"
这些硬痕迹去推断。而"用户刚刚用本工具卸载了 X"是一个**已知事实**——软件叫什么、装在哪里、
卸载前有哪些文件，全都知道。拿卸载后的磁盘状态和这个已知事实对比，得到的就是确定性残留。

两者的产出在 UI 上必须区分：通用扫描的结果叫"残留"，定向扫描的结果叫"卸载残留"，
且索引方式一栏标成"定向扫描（卸载后对比）"，否则用户会以为通用扫描漏报了别的东西。

#### 12.4.2 快照：只记"有什么"，不记"是什么内容"

`UninstallSnapshotStore` 在卸载前把安装目录递归采集成 `UninstallSnapshot`
（相对路径 + 是否目录 + 字节数），持久化为 JSON 到
`%LocalAppData%\RubbishCleaner\uninstall-snapshots\`。

**刻意不记 SHA256**：对比的目的只是回答"哪些条目消失了、哪些留下了"。
记内容哈希会让快照大几十倍、慢几十倍，而没有任何判定会因此变得更准。

**扫完即删快照**：它的使命已完成。留着不仅占地方，更会让下次误判——
用户下次再装同一个软件时，旧快照会被当成"这次卸载前的状态"。
每个软件最多保留 3 份历史快照，且按**文件名里的时间戳**排序清理
（连续 `Save` 多个快照时，文件写入时间可能落在同一毫秒，实测踩过）。

#### 12.4.3 定向扫描的三步

`UninstallResidueScanner.ScanAsync` 接收一份快照，分三步，每步独立产出：

| 步 | 做什么 | 产出 |
|---|--------|------|
| 1 | 核对快照里每个**文件**是否仍存在 | `RemainingFiles`：卸载器没删干净的具体文件 |
| 2 | 检查**安装目录本身**是否还在 | `Directories`：很多卸载器只删文件不删目录 |
| 3 | 按软件名在 `%AppData%` / `%ProgramData%` 等常见位置找同名目录 | `Directories`：数据目录才是流氓软件残留的大头 |

**为什么第 3 步可以用名字匹配**：通用扫描里名字匹配不可用（306 个顶层目录里 285 个
对不上任何已装软件，误报率 93%），是因为"不知道卸过什么"。而这里软件名是已知事实，
"刚刚卸了微信，%AppData% 下还有个 WeChat 目录"这条推理成立。

仍然保持保守：

- 短名字（< 4 字符）**只允许全等**，不允许包含匹配——否则"微信"会匹配到"微信小程序"；
- 中文两字软件名（微信、钉钉、抖音）被显式支持：`SoftwareNameNormalizer.Variants`
  的阈值从 3 降到 2，防误报的责任交给调用方（ADR-040）。

#### 12.4.4 编排：两层解耦

```
AppsViewModel（v0.2 卸载流程）
    │ CaptureBefore(app) ──► IUninstallResidueCoordinator ──► UninstallSnapshotStore.TakeSnapshot
    │ UninstallExecutor.Execute(...)          （软件自己的卸载程序接管）
    │ ReportResidueAsync(app)
    │       └─► coordinator.ScanAfterAsync ──► UninstallResidueScanner
    │                                          （拿到 UninstallResidueResult）
    └─ ResidueFound 事件 ──► MainViewModel.OnResidueFound
                               └─► LeftoversViewModel.ShowUninstallResidue(result)
```

**为什么两层都要解耦**：

1. `AppsViewModel` 通过 `IUninstallResidueCoordinator` 接口调用，不直接依赖
   `UninstallSnapshotStore`。协调者为 null 时整条链路静默关闭，
   v0.2 的卸载流程一行逻辑都不用改就能继续工作。
2. `AppsViewModel` 通过 `ResidueFound` **事件**通知上层，而不是直接引用残留页
   ViewModel——否则两个页签互相持有，改一个坏一个。

**卸载前快照失败不阻塞卸载**：用户的目的是卸掉软件，不是留下快照。
同理，卸载后残留扫描失败也绝不能影响"已经卸完了"这个事实，只记日志。

#### 12.4.5 等待 2 秒再扫

卸载器常常是异步的：主进程退出了，后台还在删文件、写日志。
立即扫会把"正在被删除的文件"当成残留报出来。因此
`UninstallResidueOptions.SettleDelaySeconds` 默认为 2，测试里设为 0
（否则测试套件会被拖慢，实测单条用例多等 2 秒）。

#### 12.4.6 真机验证

造一个 4 文件 / 1310826 字节的假软件（app.exe 1 MB + bin\lib.dll 256 KB +
unins000.exe + %AppData% 下的同名数据目录），快照后模拟卸载器只删 app.exe 与 bin\lib.dll，
扫描结果：

```
remainingFiles=1  → ...\App\unins000.exe          （卸载器没删掉自己）
removed=2/4
directories=2
  D: ...\App                 conf=High files=1 bytes=4  · 该目录是安装目录
                                                     · 卸载前 3 个文件，卸载后仍有 1 个未被删除
  D: ...\Roaming\RcE2ESoft   conf=High files=1 bytes=4  · 目录名与刚卸载的软件匹配
                                                     · 位于常见残留位置
HAS_RESIDUE=True
```

三类残留全部命中，证据链可读。

### 12.3 注册表清理

> v0.1.3 已实现其中<b>最小且最高价值</b>的一块：清理失效的 Run/RunOnce 启动项。
> 下面是已实现部分的设计，以及后续扩展的边界。

#### 12.3.1 已实现：清理残留启动项（v0.1.3）

**范围界定**：只处理 `StartupSourceKind.RegistryRunHkcu / RegistryRunHklm / RegistryRunWow64`
中**目标文件已不存在**的项。服务与计划任务明确不做——它们涉及系统机制，
误删影响面远大于一条 Run 值，需要单独设计，并由工具给出手动处理指引（见 12.3.3）。

**六道安全闸门**，按执行顺序：

| # | 闸门 | 实现位置 | 作用 |
|---|------|---------|------|
| 1 | 只选失效项 | `StartupCleaner.BuildPlan` | `entry.IsOrphan` 为 false 的直接不进计划（连"跳过"都不算） |
| 2 | 只允许 Run 类 | `StartupCleaner.BuildPlan` | 其余类型进 `Skipped` 并说明原因 |
| 3 | 要求精确坐标 | `StartupEntry.RegistryAnchor` | 强类型记录 Hive/View/SubKey/ValueName，**绝不解析 `Location` 字符串** |
| 4 | **执行前重新校验** | `StartupCleaner.Execute` | 扫描到点击确认之间程序可能被重装，此时跳过删除 |
| 5 | **先备份，失败即中止** | `StartupCleaner.WriteBackup` | 备份生成失败就一条都不删 |
| 6 | 只删值 + 删后复核 | `RegistryWriter.DeleteValue` | 绝不 `DeleteSubKeyTree`；删除后重新读取确认 |

**备份格式**：标准 `.reg`（UTF-16 LE 带 BOM），保存在
`%LocalAppData%\RubbishCleaner\backups\RubbishCleaner-启动项备份-yyyyMMdd-HHmmss.reg`。
用户双击即可还原。选择 `.reg` 而不是自定义 JSON 的理由：
用户不需要本工具也能还原——这是"可恢复性"的最强保证。

**实测验证**（真机，非模拟）：

```
造测试项 RcTest.Orphan -> D:\NoSuchDir\ghost-app.exe
执行清理 -> 只删这 1 条，其余 4 条启动项完好
备份文件 484 字节 -> reg import 后两条启动项完整恢复，值与原始一致
```

#### 12.3.2 为什么不做"删键"

一个 Run 键下通常有多个值（QQ、Firefox、Steam…）。删键会连带删掉所有值。
即使某个键下只剩一个失效值，也只删值——键本身留着不占资源，也没有副作用。

#### 12.3.3 不可自动清理项的手动指引（v0.1.4）

服务与计划任务的残留**不代劳**，但也不能让用户干瞪眼。`ManualFixAdvisor` 为它们生成：

| 类型 | 给出的内容 | 为什么这样给 |
|------|-----------|-------------|
| Windows 服务 | `sc.exe delete "服务名"` | 需管理员权限，且可能影响依赖它的服务；只给命令，由用户执行 |
| 计划任务 | `schtasks.exe /Delete /TN "\任务名" /F` | 任务名必须以 `\` 开头，否则找不到；由 `NormalizeTaskName` 自动补全 |
| 启动文件夹快捷方式 | 文件夹位置 | 删快捷方式不需要命令，给位置就够 |

**关键细节**：服务名与可执行文件名经常不一致（实测：服务名 `Winstep Xtreme Service`，
文件叫 `WsxService`）。用户很容易删错，因此当两者不一致时会额外给出醒目的提醒。

UI 上用**只读 TextBox** 而非 TextBlock 展示命令——TextBlock 无法选中，
用户没法 Ctrl+C 复制，只能手打。这个细节直接影响这个功能有没有用。

#### 12.3.4 残留计数与可清理数（v0.1.4）

v0.1.3 有个体验问题：左侧显示"残留启动项（4）"，但点清理提示"无可清理项"，
因为那 4 条全是服务类。数字和可操作性不一致会让用户反复点击。

修复：拆成两个语义明确的属性。

| 属性 | 含义 | 用途 |
|------|------|------|
| `OrphanCount` | 失效启动项总数（含服务/任务） | 筛选按钮文案、统计栏 |
| `CleanableCount` | 可自动清理的条数（仅 Run/RunOnce 且有坐标） | **清理按钮的可用性与文案** |

按钮文案按情况变化：`清理 N 条` / `无需自动清理` / `清理残留启动项`。

#### 12.3.5 后续扩展（v0.4）

- **服务类残留**：需要先判断服务是否真的停止、是否有依赖它的其他服务，
  再决定 `sc delete` 还是保留。风险等级明显高于 Run 值。
- **计划任务残留**：需要 Task Scheduler COM（`ITaskFolder.DeleteTask`），
  并处理"任务正在运行"的情况。
- ~~**孤儿注册表键**：`Uninstall` / `Software` 键判定~~ → v0.4 只做了 MSI 孤儿 Uninstall 条目，
  其余（CLSID / 文件关联 / 厂商根）见 12.5 的边界说明。
- **完整还原入口**：在 UI 里列出历史备份，支持一键回滚（而不是让用户去文件夹里双击）。

### 12.5 v0.4 注册表清理（已实现）

> 设计草案见 [v0.4-注册表清理设计草案](v0.4-注册表清理设计草案.md)。
> 这一节记录**实际实现**与草案的差异。

#### 12.5.1 范围：只有一种形态

只处理 `HKLM`（64/32 位视图）与 `HKCU` 下
`SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\{GUID}` 且 `WindowsInstaller = 1` 的条目中，
**Windows Installer 已经不认这个产品**的那些。

用户态症状：条目还留在「应用和功能」里，点卸载报错 **1639**（无效命令行参数）——
因为 MSI 认为产品不存在。删掉它只是清噪音。

明确不做：`HKCR`（COM 引用）、`HKLM\SYSTEM`（驱动/服务）、
`Software\{Vendor}` 厂商根（归属不明）、
孤儿 CLSID / 文件关联（需解析 COM 引用计数，误报率不可接受，推到 v0.5）、
MSI 内部结构（`Installer\UserData`、`Installer\Folders`）。

#### 12.5.2 实现结构

| 文件 | 职责 | 是否写注册表 |
|------|------|------------|
| `MsiInterop.cs` | `msi.dll` 最小 P/Invoke 封装：状态查询 / 产品枚举 / 属性读取 | 否 |
| `OrphanUninstallModels.cs` | `OrphanUninstallEntry`（含证据链 `Evidence` 与 `BlockReason`）+ `IOrphanUninstallScanner` | 否 |
| `OrphanUninstallScanner.cs` | 只读扫描：筛 MSI 条目 → GUID 校验 → 双确认判定 | 否 |
| `OrphanCleaner.cs` | `BuildPlan`（不查注册表）+ `Execute`（复核 → 备份 → 删键 → 再复核） | 是（仅删目标键） |
| `RegistryKeyBackupWriter.cs` | 单键**及其下所有子键**递归导出为 `.reg`（UTF-16LE + BOM），写后复核非空 | 只读源键 |

`OrphanCleaner` 的五个依赖（`backupDirectory` / `stateQuery` / `enumeration` / `deleteKey` / `keyExists`）
全部可从构造函数注入，所以清理计划与执行路径可以在**完全不碰注册表**的前提下单测。

App 层同理（v0.4.1）：`LeftoversViewModel` 现在是 **6 参数**构造函数，
前 4 个是 `ILeftoverScanner` / `Func<LeftoverCleaner>` / `Func<InstalledAppsResult>` / `Func<IReadOnlyList<SoftwareProfile>>`，
后两个 `IOrphanUninstallScanner?` 与 `Func<OrphanCleaner>?` **带默认值 `null`（即用生产实现）**。
因此 `MainViewModel` 的 4 参数调用与所有既有单测**一行都不用改**——
这是"可测化"和"不破坏既有调用点"能同时成立的写法。
不注入的话，"用户取消确认""扫描抛异常""清理后自动重扫"这些交互分支全是 0 覆盖（ADR-052）。

#### 12.5.3 `MsiQueryProductState` 的返回值处理

| 返回值 | 含义 | 处理 |
|--------|------|------|
| 1 / 2 / 3 | ABSENT（曾装过，已卸载） | 可能孤儿 |
| 4294967295 | `ERROR_UNKNOWN_PRODUCT`（MSI 数据库从未有过此产品） | 可能孤儿——**实测这是最常见的形态** |
| 4294967294 | `ERROR_INVALID_PARAMETER`（GUID 格式非法） | 可能孤儿（键名已过 GUID 正则，属异常数据） |
| 4 / 5 / 6 | ADVERTISED / INSTALLED / ADVERTISED_OR_INSTALLED | **不是孤儿**，直接返回 null |
| 0 或其他 | UNKNOWN / 未定义 / msi.dll 不可用 | **不报**（不确定就不报） |

判定还要再过一道 `MsiEnumProducts` 交叉验证：状态说 ABSENT 但枚举里有它，视为两个 API 打架，**不报**。

**枚举本身覆盖三个安装上下文**（v0.4.1 加固，ADR-050）：
旧的 `MsiEnumProductsW` 只枚举「当前用户 + 默认机器上下文」，
看不到「每用户托管 / 每用户非托管」的安装——而漏枚举的直接后果是**把在装的产品误判成孤儿**。
现在改用 `MsiEnumProductsExW` 依次枚举
`MACHINE` / `USERMANAGED` / `USERUNMANAGED`（`szUserSid = NULL` 表示当前用户，
`szProductCode = NULL` 表示该上下文下全部产品），结果取并集。
任一上下文失败只记录并继续下一个；三个全部失败才回退到旧 API——行为只会"更全"，不会"更少"。
返回类型仍是 `HashSet<string>`，调用方零改动。

本机（Windows 11 22631，AMD64，非管理员）只读实测：

| 枚举方式 | 产品数 |
|---|---|
| 旧 `MsiEnumProducts` | 344 |
| `MsiEnumProductsExW` MACHINE | 338 |
| `MsiEnumProductsExW` USERMANAGED | 0 |
| `MsiEnumProductsExW` USERUNMANAGED | 6 |
| 三上下文并集 | **344**，与旧枚举完全相等（两个方向差集都是 0） |

即本机恰好没有"藏在别的上下文里"的产品；但 `USERUNMANAGED` 那 6 个说明旧 API 是靠别的路径覆盖到它们的，
显式枚举更可靠。**多用户机器上是否真的能多枚举出产品，仍未实测。**

#### 12.5.4 七道闸门

| # | 闸门 | 实现位置 | 拦的是什么 |
|---|------|---------|-----------|
| R1 | 键名严格匹配 `{8-4-4-4-12}` | `OrphanUninstallScanner` + `OrphanCleaner.BuildPlan` | 非 GUID 的 MSI 条目结构未知，不碰 |
| R2 | 拒绝 `Uninstall` 根键本身 | `BuildPlan`（路径必须恰好是标准根 + GUID） | 删根键等于清空整个已安装列表 |
| R3 | 必须恰好是 `...\Uninstall\{GUID}`，只差一层 | `BuildPlan` | 路径拼接错误会删到上层 |
| R4 | **执行前重新查** `MsiQueryProductState`，必须仍为 ABSENT | `Execute` | 扫描到点确认之间产品可能被重装 |
| R5 | 再确认不在 `MsiEnumProducts` 列表 | `Execute` | 两个 API 打架时不删 |
| R6 | **备份必须成功且文件非空** | `RegistryKeyBackupWriter.Write` + `Execute` | 备份是底线，失败即放弃该条 |
| R7 | 删除后复核键确实不存在 | `Execute` + `KeyExistsCore` | 与 v0.1.3 的 `RegistryWriter` 同一约定 |

任一闸门拒绝都写进 `OrphanCleanupResult.Message` 如实报告，**绝不"绕过某一步直接删"**。

#### 12.5.5 备份

- 格式：标准 `.reg`（`Windows Registry Editor Version 5.00`），**UTF-16LE + BOM**
- 目录：`%LocalAppData%\RubbishCleaner\registry-backups`（`OrphanCleaner.DefaultBackupDirectory`）
- 文件名：`orphan-{键名}-{yyyyMMddHHmmss}.reg`
- 写后复核文件存在且长度 > 0，否则视为备份失败

值类型覆盖 `String` / `ExpandString` / `MultiString` / `Binary` / `DWord` / `QWord`，
默认值写成 `@=`，字符串里的 `\` 与 `"` 做转义。
读值时用 `DoNotExpandEnvironmentNames`，避免把 `%ProgramFiles%` 展开成绝对路径后再存回。

**必须递归导出子键**：删键用的是 `DeleteSubKeyTree`（整棵子树），
只备份值的 `.reg` 导入后只剩一个空壳键，子键与里面的值永久丢失——那不叫"可还原"。
每个子键在 `.reg` 里是独立的一段 `[路径]`（v0.4.1 修复，见 ADR-048）。

**32 位视图必须写成物理路径 `WOW6432Node`**（v0.4.1 修复，见 ADR-049）：
`reg import` 与双击导入都**没有视图开关**。把 `RegistryView.Registry32` 下打开的
`HKLM\SOFTWARE\...\Uninstall\{GUID}` 原样写成 `HKEY_LOCAL_MACHINE\SOFTWARE\...`，
导入时会落到 64 位视图——备份等于没用。因此 `ToRegPath` 在
`hive = LocalMachine` 且 `view = Registry32` 时输出 `SOFTWARE\WOW6432Node\...` 形式。

`HKCU` **不写** `WOW6432Node`：实测 `HKCU` 不做 WOW64 重定向，
32/64 两个视图读到的是同一份数据，而 `HKCU\SOFTWARE\WOW6432Node\...\Uninstall` 这个物理路径
根本不存在（0 个子键），硬写反而会把条目还原到错误位置。

"可还原"的验证不是"写出了个文件"，而是单测里真的走
**造键 → 导出 → 删键 → `reg import` → 断言值一致**（`Write_BackupCanBeReadBackByRegImport`）。

#### 12.5.6 UI

残留扫描页内单独一块「注册表」，与文件残留**分开扫描、分开列出**
（两者判据完全不同：文件靠硬痕迹，注册表靠 MSI API，混在一起用户分不清扫的是磁盘还是注册表）。

**两个集合，职责必须分清**（v0.4.1）：

| 集合 | 含义 | 用途 |
|------|------|------|
| `RegistryItems` | **全部**孤儿条目（判定真相） | 计数、`BuildPlan` / 清理动作的数据源 |
| `FilteredRegistryItems` | 按当前筛选条件过滤后的视图 | **界面列表实际绑定它** |

筛选与文件残留**共用同一套条件**：关键词 + 「只看可清理」。关键词匹配四个字段——
显示名、**产品码**、发行商、**完整键路径**。比文件残留多两个字段是刻意的：
注册表条目的 `DisplayName` 经常是脏数据或空的，用户手上真正能拿来搜的往往就是 GUID 或键路径。

> **筛选只影响展示，不缩小真实清理范围。** 清理动作始终基于 `RegistryItems`。
> 否则用户输入关键词后点清理，会以为"只清我筛出来的这些"，实际语义就漂移了。

**区块可见性拆成四种状态**，而不是用 `HasRegistryResidue` 一个条件：

| 属性 | 含义 | 界面表现 |
|------|------|---------|
| `ShowRegistryEmptyState` | 还没扫过 | 提示"去点扫描" |
| `ShowRegistryCleanState` | 扫过且一条都没有 | 明确告诉用户"注册表是干净的"（这是好消息，要单独说） |
| `ShowRegistryList` | 扫过且有内容 | 显示列表 |
| `ShowRegistryFilterEmpty` | 有内容但筛选全滤掉了 | 提示"当前筛选无匹配"，否则标题写着"残留 5 条"、下面却是白板，用户以为界面坏了 |

v0.4.0 用 `HasRegistryResidue` 单条件，把「还没扫」和「扫过但干净」压成同一句话——
用户看不出"要不要去点扫描"。文件残留那边一直是用 `HasScanned` 区分的，这里对齐。
`HasRegistryResidue` 属性**保留**（公开 API 没删），只是 XAML 不再拿它控制可见性。

**完整绑定表**：

| 元素 | 绑定 |
|------|------|
| 扫描按钮 | `ScanRegistryCommand`（`IsScanning` 时禁用） |
| 清理按钮 | `CleanRegistryCommand`，可用性 `CanCleanRegistry` = 可清理数 > 0 且不在扫描 |
| 列表 | `FilteredRegistryItems`，`SelectedItem` 双向绑 `SelectedRegistry` |
| 计数 | `RegistryCount` / `RegistryCleanableCount` |
| 语义化标题 | `RegistrySummaryText` |
| 四种状态可见性 | `ShowRegistryEmptyState` / `ShowRegistryCleanState` / `ShowRegistryList` / `ShowRegistryFilterEmpty` |
| 选中行详情 | `HasSelectedRegistry` 控可见性；`SelectedRegistry.FullPath`（完整键路径）、`.BlockReason`（被拦原因）、`.HiveText`（所在 hive 与视图） |

**`RegistryButtonText` 是三态，不是两态**：

| 条件 | 文案 | 为什么 |
|------|------|--------|
| 可清理 > 0 | `清理 N 个注册表残留` | 常规路径 |
| 有条目但全被闸门拦下 | `无可清理项` | 若写"无注册表残留"，用户会以为扫描没生效 |
| 一条都没有 | `无注册表残留` | 真的干净 |

**`RegistrySummaryText` 同时说明"一共看了多少条"**：
`注册表残留 2 条、可清理 1 条（其余 1 条被安全闸门拦下）` /
`注册表干净：已检查 343 个 MSI 条目，没有发现孤儿`。
不写这个数，用户会以为扫了全盘注册表——实际只看了 MSI 的 Uninstall 条目。

**选中行必须能拿到整行**：注册表条目不像目录那样能"打开所在文件夹"，
用户唯一的复核手段就是在界面上看到完整键路径，所以选中态展示 `FullPath` 而不只是展示名。

**渲染已实证，不只是属性层面对**（v0.4.1）：
用独立 STA 探针加载产品自己的 `App` + 真实 `MainWindow`，切到残留页，
注入 3 条假条目（2 条可清理 + 1 条被闸门拦下）并选中被拦下那条，确认：

| 检查点 | 结果 |
|--------|------|
| 四列表头（名称 / 版本 / 发行商 / 状态） | ✅ 就位 |
| 被拦下行的「不可自动清理」徽标 | ✅ 显示 |
| 详情区完整键路径 + 拦下原因 | ✅ 显示（`HKCU` 路径 +「不在标准 Uninstall 路径下」） |
| 标题文案 | ✅「注册表残留 3 条、可清理 2 条（其余 1 条被安全闸门拦下）」 |
| WPF 绑定追踪 | ✅ 0 错误 |

> 探针是临时验证程序，代码与截图都**没有提交进仓库**；
> 因此 `docs/progress/` 下仍然只有 v0.1.1–v0.3.1 的界面实拍。
> 若要重现，需要自己写一个 `[STAThread]` 入口：先 `new App()` 并调用其 `InitializeComponent()` 载入合并资源字典，
> 再实例化 `MainWindow` 并替换 `Leftovers` 的注入依赖为假实现——**不能直接 `new MainWindow()`**，
> 那样会因为拿不到 `Themes/Styles.xaml` 里的 `BackgroundBrush` 而抛 `XamlParseException`。

确认框逐条列出 `DisplayName（ProductCode）`（超过 15 条折叠"以及另外 N 个"），
并明确写出备份目录、双击还原方式、以及"只删 Uninstall 条目、不动软件文件"。
每条目标若被闸门拦下，`BlockReason` 会在列表里展示，**被拒项依然展示给用户**（同 ADR-036 的约定）。

## 13. 决策记录（ADR 摘要）

| ID | 决策 | 备选 | 理由 |
|----|------|------|------|
| ADR-001 | 黑名单优先于白名单 | 白名单优先 | 防"放白名单目录即洗白" |
| ADR-002 | 计划任务用 XML 解析而非 COM | `TaskScheduler` NuGet | 轻量、无第三方依赖、单文件友好 |
| ADR-003 | v0.1 不实现托盘枚举 | 逆向 `ToolbarWindow32` | 无公开 API、跨版本不稳定、产品文档已允许降级 |
| ADR-004 | 不启用 `PublishTrimmed` | 裁剪体积 | WPF 与裁剪不兼容，运行期崩溃 |
| ADR-005 | Core 不引用 WPF | 图省事放一起 | 保证可单测、未来可 CLI 化 |
| ADR-006 | 签名用 `CreateFromSignedFile` | `WinVerifyTrust` | 前者快且无需 P/Invoke；v0.1 不做吊销检查 |
| ADR-006 | ~~签名用 `CreateFromSignedFile`~~ → **已推翻**：内嵌签名 + 目录签名两级校验 | 只用 `CreateFromSignedFile` | 原以为够快够用；真机发现系统组件是 catalog 签名，会大面积误判"未签名"。见 ADR-009 |
| ADR-007 | 评分为程序画像维度，非启动项维度 | 每条启动项各自评分 | 一个软件常有多个启动点，按项评分会重复展示、分数虚高 |
| ADR-008 | 确认表**追加合并**而非整体覆盖 | 用户表覆盖内置表 | 用户误删内置白名单会导致大面积误报 |
| ADR-009 | 引入 `WinVerifyTrust` 目录签名校验 | 只做内嵌签名 | 微软系统组件普遍是 catalog 签名，不识别会把正规系统服务判成高风险 |
| ADR-010 | 引入 `NotApplicable` 评分语义 | 只有 Hit/NotHit | ①未运行进程的"无窗口"不能算已排除；②服务天然无窗口/无图标，计分会误伤 |
| ADR-011 | 伪装检测用 Damerau-Levenshtein | 普通 Levenshtein | `scvhost` 这类**换位**型伪装，普通算法距离为 2 会漏判 |
| ADR-012 | 新增无界面冒烟工具（`tools/`） | 只靠单元测试 | WPF 主程序要 UAC 无法自动化；冒烟工具直接跑真实引擎，开发期就抓出了 5 个真实缺陷 |
| ADR-013 | 失效启动项单独建模（`ORPHAN_STARTUP`，权重 0） | 沿用启发式直接打分 | 目标文件不存在时，"未签名/无窗口/无图标"全是伪信号，会把残留推成假的高风险，掩盖"该清理"这个真正有用的信息 |
| ADR-014 | 只对**绝对路径**判失效 | 所有路径都判 | 计划任务/服务的命令行常用裸文件名，由系统按 System32 解析，判失效会大面积误报正规系统任务 |
| ADR-015 | 正规厂商按**签名**加白名单（Autodesk / Tencent / NVIDIA 等） | 逐条按程序名加白名单 | 产品文档要求"知名厂商签名→直接标安全"；按名字维护是打地鼠，按签名才是稳定判据 |
| ADR-016 | 清理只处理 Run/RunOnce 的**失效**项 | 把服务、计划任务一起做 | 服务/任务涉及系统机制，误删影响面远大于一条 Run 值；先做风险最低、价值最高的一块 |
| ADR-017 | 备份用标准 `.reg` 而非自定义格式 | JSON 备份 | 用户不装本工具也能用 `reg import` 还原，这是可恢复性的最强保证 |
| ADR-018 | 执行前**重新校验**目标文件是否仍不存在 | 信任扫描结果 | 扫描到点击确认之间程序可能被重装，此时删除会破坏用户的正常启动项 |
| ADR-019 | 只删值、**绝不删键** | 键下只剩一个值时顺手删键 | Run 键下有多个值，删键会连带删掉别的启动项；键本身留着无副作用 |
| ADR-020 | 清理确认框逐条列出完整注册表路径 | 只显示"共 N 条" | 删除不可逆，用户必须能看清"到底删哪一个"，而不是盲点确定 |
| ADR-021 | 服务/任务类残留只给命令、不代劳 | 一并自动删除 | 删除服务可能影响依赖它的服务，甚至导致开机异常；这类风险必须由用户判断 |
| ADR-022 | 手动命令用只读 TextBox 展示 | TextBlock | TextBlock 无法选中复制，用户只能手打，功能等于废掉 |
| ADR-023 | 残留总数与可清理数分开建模 | 复用一个 OrphanCount | 两者语义不同：前者用于筛选展示，后者决定按钮可用性；混用会出现"显示 4 条却点不了" |
| ADR-024 | 服务名与文件名不一致时额外提醒 | 只给命令 | 实测服务名 Winstep Xtreme Service 与文件 WsxService 完全不同，用户极易删错 |
| ADR-025 | 卸载只调用软件自带卸载程序，不做强制删除 | 自己删文件+注册表实现"彻底卸载" | 强制删除极易误删，且第三方卸载器的清理逻辑更了解自己；产品合规要求"仅协助" |
| ADR-026 | rundll32 开放有条件例外 | 一律禁止系统工具 | NVIDIA 等正规软件用 `rundll32 DLL,Entry` 卸载，一刀切是误杀；放行条件是 DLL 存在且不在系统目录 |
| ADR-027 | 不自行拼接静默卸载参数 | 猜测各软件的静默参数 | `/S`、`/silent`、`/qn` 各不相同，猜错会卸载异常或卡死；要用就用注册表现成的 QuietUninstallString |
| ADR-028 | 安全拦截先于路径校验 | 按代码顺序自然排列 | 顺序错会让 `cmd.exe /c` 报"不是绝对路径"，掩盖真正原因，提示误导用户 |
| ADR-029 | 主窗口拆成两个页签 | 单列表加筛选 | "什么在偷跑"与"我装了什么"关注点不同，混一起互相干扰 |
| ADR-030 | 残留判定只信硬痕迹（孤儿卸载程序 / 失效启动项落点），**不用目录名猜** | 目录名相似度匹配 | 本机实测 306 个顶层目录里只有 21 个名字能对上已装软件；按名字判残留误报率约 93%，会把 NVIDIA Corporation、Code、Tencent 这类公共/厂商目录全判成残留 |
| ADR-031 | 文件索引 USN 直读为主、目录遍历为回退 | 只做目录遍历 / 完整 $MFT 解析 | 目录遍历整机要 10–40 秒，USN 只要 1.5–2 秒；完整 $MFT 解析约 2000 行且易在非常规卷上出错，收益不抵成本 |
| ADR-032 | 名字匹配只用于"证明有主"，且**双向**判断 | 单向（目录位于认领路径之下） | 实测 `C:\Program Files\OEM` 下有孤儿卸载程序，而其子目录"机械革命电竞控制台"是在用的已装软件；单向匹配一删就带走在用软件 |
| ADR-033 | 认领路径必须过"容器名"过滤器 | 只要路径有据就认领 | 本机多个软件的卸载器直接躺在 `C:\Program Files\<Vendor>` 下，会把 `C:\Program Files` 也认领，导致**整棵树都有主、一条残留都报不出来**（真机 E2E 实测） |
| ADR-034 | 清理只移入回收站，代码里不提供永久删除分支 | 直接删除（快、省事） | 残留判定是启发式的，误判必然发生；回收站把误判成本从"永久丢失"降为"右键还原"，且不装本工具也能还原 |
| ADR-035 | 拒绝非 DriveType.Fixed 卷 | 相信 FOF_ALLOWUNDO | 无回收站的卷（网络盘/可移动盘）上 shell 会静默降级成永久删除**且返回 0**；不预检，红线就是纸糊的 |
| ADR-036 | 安全闸门做成独立纯函数，与扫描器解耦 | 判定时顺手过滤掉危险项 | 被拒项必须展示给用户（"这里还有残留但工具不敢动"）；纯函数可以穷举单测所有拒绝分支 |
| ADR-037 | 目录级粒度清理，不做文件级 | 精确到单个残留文件 | 用户心智里的"残留"就是"某软件的残留目录"；目录也是回收站可还原的最小单位 |
| ADR-038 | 认领证据包含**被过滤掉的**注册表条目 | 只看"可展示软件" | 本机 Adobe CoreSync 的条目没有 DisplayName（不展示），只按可展示软件认领会把它目录里的 uninstall.exe 判成孤儿（真实误报） |
| ADR-039 | 厂商共享目录降为 Medium 而非直接判残留 | 只要在共享容器里就降级 / 不降级 | 不降级会把 Autodesk 授权组件判成残留；无差别降级又会把 `Program Files\Tencent\QQOld` 这类真残留降成"只提示"。必须两个条件同时成立：在共享容器内**且**命中厂商名 |
| ADR-040 | 定向扫描允许两字中文软件名，短名字只允许全等 | 一律要求 ≥ 3 字符 / 允许包含匹配 | 微信、钉钉、抖音这类两字名极其常见，一刀切要求 3 字会把它们全部漏掉；但允许包含匹配会让"微信"匹配到"微信小程序"。因此阈值降到 2，但 < 4 字符时只允许全等 |
| ADR-041 | 注册表孤儿判定**只用 MSI API**（`MsiQueryProductState` + 产品枚举双确认，v0.4.1 起枚举用 `MsiEnumProductsExW`，见 ADR-050） | ①`Classes\Installer\Products\{GUID}` 键不存在；②`InstallLocation` 目录不存在；③`LocalPackage` 不存在 | 草案原本用①，真机被反例推翻：CC Switch 的 `MsiQueryProductState` = 5 (INSTALLED)、`LocalPackage` 存在、枚举里也有它，但 `Classes\Installer\Products\{GUID}` 与 `UserData\<SID>\Products\{GUID}` **都不存在**、`reg query /s /f {GUID}` 0 命中。按①上线会把好好装着的软件删掉卸载入口。②③同样不可靠：用户手动删目录、清 `C:\Windows\Installer` 缓存都很常见，产品却仍然有效。只有 MSI 自己的数据库知道答案 |
| ADR-042 | `ERROR_UNKNOWN_PRODUCT`（4294967295）也算 ABSENT | 只认 1/2/3 三种 ABSENT | 「注册表有条目、MSI 数据库里从未有过这个产品」是**最常见的孤儿形态**。v0.4 第一版只判 1/2/3，真机 E2E 明明造了样本却报 0 个孤儿——最主要的一类全被漏掉 |
| ADR-043 | 允许 `DeleteSubKeyTree` 删键，不禁用删键 | 沿用 v0.1.3 的"只删值不删键"（ADR-019） | `Uninstall\{GUID}` 是**一个产品一个键**，键下所有值都属于这个产品，删键不影响别人；而一个 `Run` 键下挂着多个软件的值，删键必然误伤。两处语义不同，规则必须分开写，否则后来者会"统一成同一套" |
| ADR-044 | 备份固定 UTF-16LE + BOM | UTF-8（更通用）/ UTF-8 with BOM | v0.1.3 实测：UTF-8 的 `.reg` 里中文经 `reg import` 会变成问号。`reg.exe`/资源管理器只认 UTF-16LE，这是还原链路能否走通的硬约束，不是编码偏好 |
| ADR-045 | 注册表清理独立七道闸门 R1–R7，与文件残留闸门分开 | 复用 `LeftoverSafetyGuard` 的七道闸门 | 两类对象的危险面不同：文件侧要防"删到在用的目录"，注册表侧要防"删到还在的产品"和"路径拼接删到上层"。R4/R5（执行前重查 MSI）与 R6（备份非空）在文件侧没有对应物，硬套会让两套规则都变糊 |
| ADR-046 | 清理器五个外部依赖全部构造函数注入 | 直接在方法内 `new` 真实实现 | 删注册表不可撤销，测试绝不能真删。注入 `stateQuery`/`enumeration`/`deleteKey`/`keyExists`/`backupDirectory` 后，闸门拒绝、备份失败、删后复核失败等分支都能在无副作用的前提下穷举覆盖（与 ADR-036「闸门做成独立纯函数」同源） |
| ADR-047 | 备份值读取用 `DoNotExpandEnvironmentNames` | 默认展开环境变量 | 展开后再写进 `.reg`，还原出来的值是绝对路径，与原始值不一致——备份就失真了。备份必须保存**原始形态**，展开是展示层的活 |
| ADR-048 | 备份**递归导出子键**，每个子键一段 `[路径]` | 只导出值 | 删键走的是 `DeleteSubKeyTree`（整棵子树）。只备份值的 `.reg` 导入后只剩空壳键，子键与其值永久丢失——那就不叫"可还原"。删除粒度与备份粒度必须一致 |
| ADR-049 | 32 位视图导出成物理路径 `WOW6432Node` | 沿用 `HKEY_LOCAL_MACHINE\SOFTWARE\...` | `reg import` 与双击导入**没有视图开关**，原样写会落到 64 位视图，备份形同虚设。本机实测 `reg query /reg:32` 的 241 个子键与 `...\WOW6432Node\...\Uninstall` 的 241 个完全一致；`HKCU` 不做重定向（32/64 同数据，且 `HKCU\SOFTWARE\WOW6432Node\` 路径不存在），故 HKCU 保持原样 |
| ADR-050 | 改用 `MsiEnumProductsExW` 枚举 MACHINE / USERMANAGED / USERUNMANAGED 三上下文并集 | 只用 `MsiEnumProductsW` | 旧 API 看不到每用户托管/非托管安装，**漏枚举 = 把在装产品判成孤儿 = 误删**。任一上下文失败继续下一个，三个全失败才回退旧 API，保证只会"更全"不会"更少"；本机并集与旧枚举都是 344 个、双向差集 0 |
| ADR-051 | 「拒绝 `Uninstall` 根键」（R2）显式判断，且放在 GUID 校验之前 | 靠 R3 的路径相等间接成立 | 显式判可以同时拦住两种退化：`ProductCode` 为空导致拼接结果退化成根键、`UninstallRootPath` 本身被当成目标。放在最前面是因为它拦的是最坏情况（删根键等于清空整个已安装列表） |
| ADR-052 | App 层的扫描器与清理器工厂也走构造注入 | 沿用 v0.4.0 的硬编码字段 | v0.4.0 里 `_registryScanner` / `_registryCleanerFactory` 直接 `new` 真实实现，导致"用户取消确认""扫描抛异常""清理后自动重扫"这些分支 0 覆盖。注入后全部可测，且不需要真删任何注册表（与 ADR-046 同理，只是上移一层）。后两个参数带默认值，既有 4 参数调用点零改动 |
| ADR-053 | 注册表列表绑 `FilteredRegistryItems`，清理仍基于 `RegistryItems` | 列表直接绑 `RegistryItems`（简单） / 清理也走筛选结果 | 筛选必须能作用于注册表条目（用户手里往往只有 GUID 或键路径），但**筛选只能影响展示、不能缩小清理范围**——否则"我筛了一下再点清理"会静默变成"只清这些"。两个集合分别表达"判定的真相"和"当前的视图" |
| ADR-054 | 注册表区块用四种独立状态属性（未扫 / 干净 / 有内容 / 筛选空），不用单条件 | 沿用 `HasRegistryResidue` 一个布尔 | 「还没扫」和「扫过但干净」对用户是两件完全不同的事：前者要提示去点扫描，后者要恭喜他。压成一个 `Count == 0` 会让用户看不出区别（文件残留那边一直用 `HasScanned` 区分，此处对齐）。另外「筛选把条目全滤掉」必须单独提示，否则标题写"残留 5 条"、下面白板，用户以为界面坏了 |
| ADR-055 | `RegistryButtonText` 三态，`RegistrySummaryText` 附带"已检查 N 个 MSI 条目" | 两态（可清理 / 无残留）；标题只写残留数 | 扫到 N 条但全被闸门拦下时，按钮若写"无注册表残留"，用户会以为扫描没生效（同 ADR-023 的计数语义教训）。标题不写"已检查 N 条"，用户会以为扫了全盘注册表——实际只看了 MSI 的 Uninstall 条目 |
| ADR-056 | UI 语义用「真实窗口渲染」验证，而不只看 ViewModel 属性 | 只写属性级单测 | 属性全绿但界面不刷新/不显示，是本项目反复踩过的坑（v0.1 的表头列名消失、v0.3 的清理结果被覆盖）。v0.4.1 用 STA 探针加载真实 `App` + `MainWindow` 注入假条目实测：四列表头、被拦徽标、键路径详情、标题文案、绑定追踪 0 错误。**但探针与截图未入库**，属一次性验证，回归无自动化保护 |
| ADR-057 | 「是绝对路径」闸门同时要求 `Path.IsPathRooted` **和** `Path.IsPathFullyQualified`；`IsVolumeRoot` 先判原始输入是否完全限定 | 只用 `Path.IsPathRooted`（v0.3 起） | `Path.IsPathRooted("D:")` 返回 **true**——驱动器相对路径也算 rooted，但它不是绝对路径，语义是「D 盘的当前目录」。它会被 `GetFullPath` 按进程隐藏变量 `=D:` 补全：有该变量得到 `D:\某目录`，没有则得到 `D:\`（**盘根**）。实测同一份代码因此在不同环境得出相反结论。后果有两层：① 测试随机红（开发者机器绿、干净环境红）；② 真缺陷——`Check("D:")` 能通过第一道闸门，然后层级/保护路径判断作用在一个语义不确定的路径上。修法是「在补全之前判原始输入」（与进度文档第 24 条缺陷同源） |

## 14. 已知限制

### 14.1 v0.1 ~ v0.2 仍然存在的限制

1. 托盘图标无法判定（ADR-003）。
2. 计划任务在非管理员下可能不完整（已降级提示）。
3. 签名校验不检查吊销状态（`WTD_REVOKE_NONE`）。
4. 不检测 Winlogon / AppInit_DLLs / IFEO。
5. 内置黑名单为示例规模（6 条），需持续维护。
6. 32 位系统未做验证（目标平台仅 Win10/11 x64）。
7. 检测结果为**建议性**；清理动作一律可还原（注册表备份成 `.reg`，文件移入回收站）。
8. 目录签名无法取到证书主体，只能用"是否在 `%SystemRoot%` 下"近似判定微软归属。
9. 快捷方式索引的名称匹配是"包含"关系，同名程序可能被误判为"有入口"（属保守方向，少扣分）。
10. 纯服务型程序不参与三条 UI 相关规则，因此"确实没有界面的流氓服务"只能靠签名/伪装/黑名单识别。
11. 卸载只能调用软件自带卸载器，不强制删除文件，也不拼接静默参数（ADR-025 / ADR-027）。

### 14.2 v0.3 新增的限制

12. **残留判定只看卸载注册表**。归属证据来自 `Uninstall` 键的 `InstallLocation` 与卸载命令路径，
    不查 CLSID、文件关联、服务 `ImagePath`。因此"注册在别处"的组件可能误报
    （本机实测 1 例：Autodesk 授权组件，已降级为 Medium 并被安全闸门拦住）。
13. **USN 索引对硬链接只保留一个名字**。NTFS 硬链接是"一条 MFT 记录、多个目录项"，
    索引里只看到其中一个；命中文件会额外用 `FindFirstFileNameW` 展开，但没有做全量多名字索引。
14. **USN 索引需要管理员权限**。标准用户下卷句柄返回 err=5，只能退回目录遍历（慢一个数量级）。
    两种模式的结果已做交叉验证（`C:\Windows` / `System32` / `Common Files` 缺失 0、多余 0），
    但仍属于"两套实现"，长期看有漂移风险。
15. ~~**残留扫描与卸载流程未联动**~~ —— v0.3.1 已完成（卸载前自动快照 → 卸载后定向扫描 → 残留页直接展示）。
16. **提权下全盘索引峰值约 110 MB**（单卷 C:），扫完立即 `Release()` 归零。
17. **非固定磁盘上的残留一律不清理**（`FOF_ALLOWUNDO` 在无回收站的卷上会静默降级成永久删除，ADR-035）。

### 14.3 v0.3.1 新增的限制

18. **快照只覆盖 `InstallLocation`**。注册表没写安装位置的软件做不了快照，
    联动会自动降级为"什么都没发生"（不报错、不阻塞卸载）。
19. **快照是目录级而非文件内容级**：只对比"条目在不在"，不对比"内容变没变"。
    卸载器改写同名文件的情况不会被发现（刻意如此，理由见 12.4.2）。
20. **快照默认等 2 秒**才扫描（等卸载器后台收尾），用户会觉得"卸载完多等了一下"。
21. **快照按软件名存放**：同名软件先后安装两次时，`LoadLatest` 取的是最近一次，
    需要靠 `TakenAt` 时间戳人工区分。

### 14.4 v0.4 新增的限制

22. **只处理 MSI 条目**。`WindowsInstaller != 1` 的 Uninstall 条目（NSIS / Inno / 自研安装器）
    没有可靠的"产品是否还存在"判据，v0.4 一条都不动——它们点卸载报错只会是"找不到卸载程序"，不是 1639。
23. **每用户安装产品的多用户视角**。改用 `MsiEnumProductsExW` 覆盖三个上下文后，
    "漏枚举"这条风险已经收窄；但 `szUserSid = NULL` 仍表示**当前用户**，
    别的用户装的产品在本用户视角下是否会被正确枚举——**未实测**（本机只有单个真实用户账户）。
24. **真实僵尸样本仍然不足**。v0.4 的 E2E 用的是程序化造的样本（`{DEADBEEF-...}`），
    本机 344 个 MSI 条目全部有效；造样本能验证代码路径，**不能证明判据在真实脏环境里同样可靠**。
25. **删除不可逆，只能靠 `.reg` 还原**。键被删后 MSI 数据库里对应记录不会自动清理，
    也不提供"后悔"按钮——还原要用户自己去 `registry-backups` 双击 `.reg`。
26. **UI 端到端点击验证未做**。提权窗口的 UIA 自动化在本机不稳定（v0.1 起就踩过），
    v0.4 的 UI 逻辑靠 App 单测覆盖，Core 链路靠真机 E2E 覆盖，两者之间没有自动化接缝。
27. **注册表子键深度有上限**。递归导出设了最大深度保护（正常 `Uninstall` 条目只有一两层子键）；
    超过上限的异常深树会被截断，此时备份不完整——属已知边界，不在正常数据形态内。

### 14.5 已知的启动期异常（已排除 XAML 缺陷）

偶尔在启动时出现：

```
System.Windows.Markup.XamlParseException
  'Provide value on System.Windows.StaticResourceExtension' 引发异常
  行号 10，行位置 11 → Background="{StaticResource BackgroundBrush}"
```

**这不是 XAML 的缺陷**，已定位并排除：

- `BackgroundBrush` 定义在 `src/RubbishCleaner.App/Themes/Styles.xaml`（由 `BackgroundColor` 派生），
  它**只**通过 `App.xaml` 的 `ResourceDictionary.MergedDictionaries` 注入应用级资源。
- 因此任何绕开 `App` 的 `InitializeComponent()`、直接 `new MainWindow()` 的加载方式，
  都必然找不到该资源并抛出**同一条** `XamlParseException`（行号 10 完全一致）——这是可稳定复现的。
- 正常启动（`App` 先载入合并字典再构建窗口）时 0 错误。

结论：这是「构建过程中程序集被重写到一半，进程仍按旧/不完整状态加载」的**竞态**，
多见于构建刚结束就立刻启动。重跑或等构建结束即恢复正常，不需要改代码。

> 记录这条的目的是**免得后人再排查一次**：看到行号 10 的 `StaticResource` 报错，
> 先确认是不是在构建中途启动，而不是先去改 XAML。
