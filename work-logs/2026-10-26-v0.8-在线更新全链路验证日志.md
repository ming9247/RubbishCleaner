## 本轮目标

用户要求：**不是单测，是真实 HTTP + 真实写盘**——在真实机器上把 TrustTableUpdater
的在线更新整条链路跑一遍，产出实测结论，而不是"测试绿了所以应该没问题"。

要验证的七件事：

1. 检查更新：远程 v2 vs 本地无用户层（v0）→ 期望 `Available=true`；
2. 执行更新：真实下载 + 真实写盘到用户层，版本 0 → 2；
3. 复验写盘：重读文件，JSON 可解析，版本/条目数与远程一致（白 19 / 黑 7）；
4. 再次检查：应判定"已是最新"，`Available=false`；
5. 回滚：删掉用户层文件后重读，应回落内置表（v1 / 白 9 / 黑 6）；
6. 联网守卫：EnableNetworking=false 时**直调** CheckUpdateAsync / UpdateNowAsync，
   应被拦住且一次请求都不发出；
7. **真实默认路径**：必须至少用生产构造函数 `TrustTableUpdater()` 跑一次
   `%ProgramData%\RubbishCleaner\trust-table.json`，证明生产路径可用，跑完恢复原状。

## 核心约定（延续此前各版）

- **只写用户层**（ADR-008）：在线更新只写 `%ProgramData%\RubbishCleaner\trust-table.json`，
  内置表与程序目录表永不覆盖；删掉用户层文件即回退旧特征库。
- **联网必须 opt-in**：AppSettings.EnableNetworking 默认 false；
  SettingsViewModel.CheckUpdateAsync / UpdateNowAsync 入口都有 CanUseNetwork 守卫，
  守卫不依赖按钮 CanExecute（v0.7 的"直调绕过按钮"踩坑即由此修复）。
- **探针不污染机器**：写盘目标、settings.json、日志目录全部重定向到临时目录；
  唯一碰真实路径的 [g] 段先记录原状态，跑完删除并恢复。
- **探针不碰产品代码**：本轮只新增 `tools/RubbishCleaner.TrustE2E/`，
  `src/` `tests/` `docs/` `README.md` 一行未改。

## 主要改动

### 新增 tools/RubbishCleaner.TrustE2E（一次性验证探针，不进主程序）

- `RubbishCleaner.TrustE2E.csproj`：net8.0-windows 控制台，引用 Core + App
  （要 App 是因为 [f] 段要直接驱动 SettingsViewModel，UseWPF 仅为让 App 项目可被引用）。
- `Fakes.cs`：三个探针专用类型
  - `CountingDownloader : HttpDownloader`——重写 virtual 的 DownloadFileAsync 只做计数，
    用来证明"守卫拦下时一次请求都没发"；
  - `ThrowingBackupStore : IBackupHistoryStore`——三个成员全部抛 NotSupportedException，
    探针不涉及备份；
  - `SyncProgress<T> : IProgress<T>`——同步回调。`Progress<T>` 无同步上下文时把回调
    丢到线程池，探针需要在 UpdateAsync 返回前就拿到完整进度序列，故自己实现。
- `Program.cs`：八段检查 [0] [a]–[g]，`Check(name, ok, detail)` 累计失败项，
  全通过退出码 0、有失败退出码 2；失败时保留探针目录供排查，全通过才删。
- `TlsDiagnostics.cs`：`--tls-diag` 诊断模式，把 TLS 失败挖到最内层原因
  （环境变量 / DNS / 原始 SslStream 握手 / 证书链 / 默认 HttpClient / 关闭吊销检查的 SocketsHttpHandler）。
  这个文件是本次踩坑 1 的直接产物。

## 本轮踩坑

1. **首跑 21 项全挂：TLS 握手失败**。第一次运行 [0]/[a]/[b]/[c]/[d]/[e].7/[g] 共 21 项失败，
   错误一律是 `HttpRequestException: The SSL connection could not be established, see inner exception.`
   （HttpDownloader 重试 2 次后放弃，每次约 3.3–3.9 s）。当时必须先排除"是不是代码/环境问题"，
   于是做了三方对照：
   - `curl.exe` 同一 URL：HTTP 200 / 2383 B / 0.72 s，**IPv4 与 IPv6 都通**（185.199.109.133 与 2606:50c0:8001::154）；
   - 进程内全新 `HttpClient`（[0] 段）：同样报 SSL 失败——说明不是 HttpDownloader 的锅；
   - `--tls-diag`：环境变量无代理、DNS 正常、原始 `SslStream` 握手成功（TLS 1.3 / TLS_AES_128_GCM_SHA256，
     证书链 `*.github.io → YR1 → Root YR → ISRG Root X1`，证书校验回调 `errors=None`）、
     默认 HttpClient 与关闭吊销检查的 SocketsHttpHandler 也都 HTTP 200。
   结论：**机器网络与证书链本身没问题，是首次运行时的瞬时失败**（重试 2 次均撞在同一时间窗）。
   修法：不改产品代码，把失败如实记进日志后复跑——复跑即全通过，随后连跑三次稳定。
   这次失败没有掩盖：探针在失败时保留临时目录与日志，可直接复查。

2. **类注释说"两阶段提交"，但目标写入不是原子的**。`TrustTableUpdater` 类注释写
   "采用先写临时文件、校验后再替换的两阶段提交模式"，实际代码里"先写临时文件、校验"
   发生在**下载阶段**（HttpDownloader 写 `.tmp` 再 Move，CheckUpdateAsync 写
   `Path.GetTempFileName()`），而**最终落到 `_targetPath` 的是直接
   `File.WriteAllTextAsync(_targetPath, remoteJson)` 覆盖写**，没有 temp→rename。
   风险：写到一半进程被杀会留下截断的 trust-table.json。影响可控——TrustTableLoader
   的 `TryLoadFile` 解析失败返回 null，会静默回退内置表，不会崩；但"两阶段提交"这个
   描述对最终写入并不成立。本轮只记录，不改代码（改动属于 src/ 范围，不在本任务写权限内）。

3. **`HttpDownloader` 对非 2xx 不重试**。重试循环只覆盖异常路径；HTTP 404/500 直接
   `Success=false` 返回（`HTTP {code}: {reason}`）。远程文件被删或路径写错时不会重试，
   属于设计选择，但与"maxRetries=2"的字面预期不同，记一笔。

4. **`Progress<T>` 在无同步上下文的控制台里丢回调时序**。探针是控制台程序，
   `Progress<T>.Report` 会把回调 post 到线程池，`UpdateAsync` 返回时进度可能还没打完，
   导致"进度序列"断言时有时无。修法：探针自己写 `SyncProgress<T>` 同步回调。

5. **ImplicitUsings 在探针项目里没带上 System.IO**。csproj 已 `ImplicitUsings=enable`，
   但 `Program.cs` 里 `Path`/`File`/`Directory`/`FileInfo` 全部 CS0103/CS0246（45 个错误）。
   修法：显式补 `using System.IO;`（`UseWPF=true` 的 SDK 默认 using 集合里没有 System.IO）。

## 遗留

1. **`CurrentVersion` 语义与用户直觉不一致**：`CheckUpdateAsync` 只读用户层文件算
   `CurrentVersion`，不读三层合并结果。干净机器上内置表已是 v1，但界面会显示"当前 v0"；
   回滚删文件后同样显示 v0。功能上无碍（v0 < v2 仍会提示更新），但文案会让人以为本地没有特征库。
   建议后续让 `CurrentVersion` 取 `TrustTableLoader.Load()` 的合并版本。
2. **最终写入非原子**（踩坑 2）：建议改成"写 `_targetPath + ".tmp"` → `File.Move(tmp, target, overwrite: true)`"，
   与 HttpDownloader 内部做法保持一致。
3. **`DefaultGitHubRawUrl` 仍指向占位仓库**：本次实测能 200 说明 `ming9247/RubbishCleaner`
   的 raw 地址当前真实可达（2383 B 与仓库内 `src/RubbishCleaner.App/Resources/trust-table.json`
   一致），但项目正式发布前需确认该仓库确为官方仓库。
4. **探针未进 `RubbishCleaner.sln`**：本轮写权限只到 `tools/RubbishCleaner.TrustE2E/`，
   改 sln 属于根目录文件。要常态化（例如每次发版前跑一次）需要另行授权把项目加进解决方案。
5. **首次运行的 TLS 瞬时失败未复现**：只发生过一次，无法确定根因（本机网络瞬时抖动 / 中间设备
   干扰最可能）。若后续在用户机器上复现，`--tls-diag` 可直接定位到具体环节。
