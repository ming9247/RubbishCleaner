# 2026-10-24 开发日志 —— v0.3.0 残留目录扫描与可还原清理

## 目标

产品文档里 v0.3 是"残留文件扫描（MFT 直读）"。这一版要回答用户第三个问题：
**我卸载过的东西，还剩下什么？**

这一版的难点不在"扫描"本身，而在**判定**——什么才算"残留"。判错了，用户就丢数据。

## 一、最重要的一个决定：不靠名字猜

动手前先做了一个实验：把 5 个常见根目录（Program Files / Program Files (x86) /
ProgramData / LocalAppData / Roaming）的顶层目录全部列出来，和已安装软件列表做名字匹配。

结果：

| 口径 | 数量 |
|------|------|
| 顶层目录总数 | **306** |
| 名字能对上已安装软件 | **21** |
| 名字对不上 | **285** |

如果按"名字对不上 = 残留"来做，误报率大约 **93%**。

而那 285 个绝大多数**确实是已装软件的目录**，只是名字对不上：

```
C:\Program Files\NVIDIA Corporation          # 驱动装在别处，这是共享数据目录
C:\Users\taco\AppData\Local\ASP.NET          # .NET 运行时的公共缓存
C:\Users\taco\AppData\Roaming\Code           # VS Code 的用户数据
C:\Users\taco\AppData\Roaming\Tencent        # 厂商根，下面挂着 QQNT / WeChat / QQLive
C:\ProgramData\Intel Package Cache {GUID}    # 安装器缓存
```

所以判定哲学直接反过来：**名字匹配只用来"证明这个目录有主"（避免误报），
不用来"证明它是残留"。** 判残留只信两类硬痕迹：

1. **孤儿卸载程序**：目录里还留着 `unins000.exe` / `uninst.exe` / `uninstall.exe`，
   而**没有任何已安装软件认领这个目录**。卸载程序的存在本身就证明"这里装过软件"。
2. **失效启动项落点**：启动项指向的 exe 没了，但它所在目录还在，且无人认领。

第二条还救回一个真实的坑：本机 `C:\Program Files\OEM` 下有一个孤儿卸载程序，
但它的子目录 `C:\Program Files\OEM\机械革命电竞控制台` 是**在用的已装软件**。
如果"认领"只做单向（目录在认领路径之下才算有主），父目录会被判成残留，
一删就把在用的软件连带删掉。所以认领判定改成**双向**。

## 二、全盘索引：USN 直读 + 目录遍历回退

```
CreateFile("\\\\.\\C:", GENERIC_READ, share=RW|DELETE, OPEN_EXISTING, FILE_FLAG_BACKUP_SEMANTICS)
  → DeviceIoControl(FSCTL_ENUM_USN_DATA)
  → 每条 USN_RECORD 给出 (FRN, 父FRN, 名字, 属性)
  → FRN→(父FRN,名字) 字典 + 父子链回溯得到路径
```

| 实现 | 权限 | 本机实测 |
|------|------|---------|
| `UsnFileIndex` | 需管理员 | C: 82.6 万条 / 1.5 秒 / 峰值约 110 MB；D: 53.1 万条 / 2.2 秒 |
| `FallbackVolumeFileIndex` | 标准用户可用 | 同 5 个根目录约 3–20 秒，结果一致 |

**为什么不做完整 `$MFT` 解析**（Everything 方案）：要解析 NTFS 引导扇区、
`$MFT` 的 DATA 运行列表、属性头、压缩与稀疏标志，约 2000 行，且极易在非常规卷上出错。
USN 枚举把这一切交给内核，1.5 秒已经够"用完即走"。

## 三、E2E 抓出来的三个真实缺陷（这一节最值得记）

功能全部写完、单测全绿之后，我在真机上跑了完整 E2E（造样本 → 扫描 → 进回收站 → 还原 → 校验字节数）。
**前两次都失败了**，抓到三个单测永远发现不了的问题：

### 缺陷 1：自己造的残留样本扫不出来

把样本造在 `C:\Program Files\RcE2ELead_*`，扫描器视而不见。

根因：认领集合里有 `C:\Program Files`。本机有多个软件的卸载程序直接躺在
`C:\Program Files\<Vendor>` 下，而"把卸载器所在目录的上一级也算认领"这条规则
（本来是为了解决 `Vendor\Product` 的注册表缺陷）把它认成了软件目录。
一旦 `Program Files` 被认领，**整棵树都变成"有主"**。

讽刺的是：这条规则我在写的时候就防了"不要加祖先目录"，却没防住"上一级本身就是容器"。

修法：认领路径要求层级 ≥ 3，且末端不是 `Program Files` / `ProgramData` / `AppData` /
`Common Files` 这类容器名。

### 缺陷 2：Adobe CoreSync 的目录被判成孤儿（真实误报）

`C:\Program Files (x86)\Adobe\Adobe Sync\...\customhook\uninstall.exe` 被判成残留。

根因：CoreSync 的注册表条目**没有 DisplayName**，被"可展示软件"的过滤规则丢弃，
于是它的目录在认领集合里不存在。

**这个缺陷暴露的是架构问题**：残留判定用的是"可展示软件列表"，而"可展示"是给人看的过滤，
与"这个目录有没有主"根本是两件事。一个 `SystemComponent=1` 的补丁、一条没有名字的组件条目，
在磁盘上占的目录同样是有主的。

修法：`InstalledAppEnumerator` 新增 `ClaimPaths`，把**所有**条目的路径证据都收集起来
（含被过滤的），残留扫描一并使用。

### 缺陷 3：Autodesk 授权组件被判成残留

`C:\Program Files (x86)\Common Files\Autodesk Shared\AdskLicensing` 里有一个 6 MB 的
`uninstall.exe`，注册表里**确实没有**对应的 Uninstall 条目（Autodesk 用它自己的 ODIS 管理），
但 AutoCAD 的授权组件正在用它。

修法：位于 `Common Files` / `Shared` / `ProgramData` 这类"共享容器"下、且路径命中某个
已装厂商名的，降为 Medium（只提示、不自动清理）。

**这里差点走错**：第一版我写成"只要路径命中厂商名就降级"，结果
`Program Files\Tencent\QQOld` 这种真残留也会被降掉，清理能力被削没了。
正确的是<b>两个条件同时成立</b>：在共享容器内 **且** 命中厂商名。

> 这三个缺陷有个共同点：**都不是逻辑写错了，而是"我以为的事实"和真机不一样**。
> 单测能验证逻辑自洽，只有 E2E 能验证事实。

## 四、踩的坑（这一版尤其多）

### 坑 1：`HighUsn` 传 `ulong.MaxValue` 会拿到 0 条记录

第一次跑 `FSCTL_ENUM_USN_DATA`，返回 `ERROR_HANDLE_EOF(38)`，**一条记录都没有**。

看起来像"权限不够"或"卷不支持"。查下来是输入结构的第三个字段 `HighUsn`
传了 `ulong.MaxValue`(0xFFFF…FFFF)，内核把整个范围判为空。
改成 `long.MaxValue`(0x7FFF…FFFF) 立刻正常。

### 坑 2：标准用户读卷永远 err=5

本机 `EnableLUA=1`，即使账户在 Administrators 组里，未提权的进程也拿不到卷句柄。
试了 `GENERIC_READ`、`0`、`0x80`、`0x120089` 等访问权限组合，全部 `err=5`。

结论：标准用户下 USN **不可能**可用，必须有回退实现。而且这件事必须**如实告诉用户**——
不能在标准用户下扫了 20 秒还让用户以为做了全盘秒级扫描。

### 坑 3：`Path.GetFullPath` 把相对路径静默补全，让"拒绝相对路径"这道闸门失效

安全闸门里本来写了"不是绝对路径就拒绝"，但代码是先 `Path.GetFullPath` 再
`Path.IsPathRooted` —— 前者已经把 `AppData\Local\Foo` 补成绝对路径，后者自然永远为真。

修法：**在补全之前**判断原始输入。顺手补了一条单测锁死这个行为。

### 坑 4：`FOF_ALLOWUNDO` 会静默降级成永久删除

`SHFileOperationW` 在**没有回收站的卷**（网络盘、可移动盘）上，会忽略 `FOF_ALLOWUNDO`
直接永久删除，**而且照样返回 0**。

这意味着"只移入回收站"这条红线在那种卷上是纸糊的。
修法：删除前预检卷类型，非 `DriveType.Fixed` 一律拒绝。

### 坑 5：XAML 里 `StringFormat=· {0}` 报"找不到 Extension 程序集"

`{0}` 被 XAML 解析器当成标记扩展。改成两个 `<Run>` 拼接。
（和 v0.1 那次 `StringFormat` 导致的"表头列名消失"是同一类问题的不同表现。）

### 坑 6：清理完了，状态栏立刻变回"扫描完成"

清理成功后会重新扫描刷新列表，而重扫会覆盖 `StatusText`。
用户刚点完清理，最该看到的是清理结果，不是"扫描完成"。
修法：重扫之后把清理结论写回去。

### 坑 7：清理按钮说"可清理 5 项"，实际只清了 3 个

`CleanableCount` 只判断了安全闸门（`CanDelete`），没有判断置信度。
低置信度的项虽然 `CanDelete=true`，但 `BuildPlan` 会拒绝它们。

两个条件必须一致：通过闸门**且**置信度为 High。

（这和 v0.1.4 那个"显示 4 条残留却点不了清理"是同一类问题的镜像：
一个是数字大于可操作性，一个是数字大于实际可操作性。）

## 四、安全设计：闸门与扫描彻底解耦

`LeftoverSafetyGuard` 是一个**纯函数**：输入路径与上下文，输出"允许/拒绝 + 中文原因"。
七道闸门按顺序执行：

| # | 闸门 | 拒绝示例 |
|---|------|---------|
| 1 | 非空、可解析、**原始输入**是绝对路径 | `AppData\Local\Foo` |
| 2 | 不是盘根 | `C:\` |
| 3 | 层级足够（≥ 2 级） | `C:\Program Files` |
| 4 | 不在系统保护路径下 | `C:\Windows\SysWOW64\X`、`…\Common Files\Vendor` |
| 5 | 不与系统保留名冲突 | `…\Microsoft`、`…\Package Cache` |
| 6 | 与本程序所在目录不重叠 | 删 `D:\Tools` 会删掉正在运行的自己 |
| 7 | 不是重解析点（符号链接/目录联接） | 删链接会牵连真实目标 |

**被拒的项依然展示给用户**，只是标记"不可自动清理"。
用户需要知道"这里还有残留，但工具不敢动"。

清理层 `LeftoverCleaner.Execute` 只接受"移入回收站"这一种删除方式，
代码里**没有** `File.Delete` / `Directory.Delete` 的兜底分支——
这是刻意留下的空洞：清理残留永远不该是不可逆的。

## 六、这一版没做的

- **卸载后自动触发该软件的残留扫描**：现在要用户自己切到残留页点扫描。
  联动需要"卸载前后快照对比"，留到 v0.3.1。
- **硬链接去重**：USN 按 MFT 记录枚举，一条记录只回一个名字，硬链接是"一条记录、
  多个目录项"，所以索引里只能看到其中一个名字。已在需要时补 `FindFirstFileNameW` 展开，
  但没做全量的多名字索引。
- **注册表残留**：仍在 v0.4，需要 CLSID/文件关联联合校验，风险等级高于文件残留。

## 七、给下一版的提醒

1. **别为了"检出更多"放宽判定**。这一版在真实机器上误报 0，靠的就是"只信硬痕迹"。
   每加一条新判据，都要先问：它能不能在真实机器上产生 0 误报？
2. **回退实现必须和主实现结果一致**，否则安全判定会随权限漂移。
   建议每次改索引层都跑一次"USN vs 目录遍历"逐个比对的交叉验证。
3. **清理永远走回收站**。这条红线上次（v0.1.3 备份 .reg）和这次（回收站）都是同一个思路：
   把不可逆操作变成可逆操作，用户才敢用。
