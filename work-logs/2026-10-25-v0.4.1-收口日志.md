## 一、为什么需要收口

v0.4.0 提交时，代码是绿的、测试是过的、真机 E2E 也是通的。那为什么还要再开一版？

因为**"能跑"和"自洽"是两件事**。收口前梳理出来的问题分三类：

| 类型 | 具体问题 | 后果 |
|---|---|---|
| 真 bug（可还原性） | `RegistryKeyBackupWriter.ToRegPath` 对 `HKLM` + `RegistryView.Registry32` 也输出 `HKEY_LOCAL_MACHINE\SOFTWARE\...`，而 `reg import`/双击都没有视图开关 | 32 位条目的备份会还原到 64 位视图，"双击可还原"这条底线在 32 位视图上**不成立** |
| 完整性缺口 | `BuildRegContent` 只导出值、不导出子键 | 孤儿键下若有子键，还原后结构不完整 |
| 判定缺口 | `MsiEnumProducts` 只按当前用户/机器默认上下文枚举 | 多用户机器上别人的每用户产品可能既"状态 ABSENT"又"不在枚举里"→ 误判 |
| 质量缺口 | `LeftoversViewModel` 的 `_registryScanner` / `_registryCleanerFactory` 是硬编码字段 | v0.4 的 App 层交互（取消确认、扫描异常、清理失败重扫）**0 测试覆盖** |
| 文档缺口 | README 顶部还写 v0.3.1，没有注册表清理章节；技术设计文档的「后续扩展（v0.4）」还写着"孤儿注册表键待做"；进度文档测试数写的是 327 | 新人读完文档会以为 v0.4 没做，或者做了另一件事 |

前四类由 Core / App 两位 teammate 处理，**我负责最后一类**：让文档与代码自洽。

文档工作的难点不是"写"，而是**每写一句话都要能指出代码里对应的位置**。
指不出来，那句话就得写"待实测"——这也是本轮唯一让文档变长的原因。

## 四、顺手发现的一个坑（不在任务范围内，如实报告）

在**快照所在的目录**第一次跑测试时，出现 1 个失败：

```
失败 RubbishCleaner.Core.Tests.LeftoverSafetyGuardTests.IsVolumeRoot_RecognizesRootsAndSubdirectories [1 ms]
  Assert.False() Failure
  Expected: False
  Actual:   True
  → LeftoverSafetyGuardTests.cs:143
```

用例断言 `LeftoverSafetyGuard.IsVolumeRoot("D:")` 应为 false（"D:" 是驱动器相对路径，不是盘根）。
把同一份代码换到 **D 盘目录**下跑，这条就过了。

根因判断（**未逐行验证，属推测**）：`IsVolumeRoot` 用 `Path.GetFullPath("D:")` 解析，
而驱动器相对路径会按"该盘当前目录"补全；进程当前目录在哪个盘、进程有没有设置过该盘的当前目录，
会影响 `GetFullPath("D:")` 的结果。也就是说这条用例**依赖运行环境的当前工作目录**。

处置：我当时**没有改代码也没有改测试**（`src/`、`tests/` 不在我的 write scope），
只把现象、推测根因与两种候选修法写进日志交给 Lead。

### Lead 随后用真实探针证实了根因，并修掉了一个真缺陷

推测被证伪了一半，值得记下来：

| 我的推测 | 实测结果 |
|---|---|
| 根因是 `Path.GetFullPath("D:")` 受进程当前目录所在盘影响 | **部分对**：真正影响它的不是"当前目录在哪个盘"，而是进程里那个**隐藏环境变量 `=D:`（每盘当前目录）** |

证据（Lead 用一个刻意构造的干净子进程对比）：

```
正常进程（带 =D: 变量）      GetFullPath("D:") = D:\Rubbish-cleaner    → IsVolumeRoot 判 false（用例绿）
清空环境启动的子进程（无 =D:）GetFullPath("D:") = D:\                  → IsVolumeRoot 判 true （用例红）
```

也就是说：**同一条用例的通过与否，取决于跑它的进程里有没有那个隐藏变量**。
CI、不同的 shell、不同的启动方式都可能改变它——这是"摇色子"，不是"逻辑正确"。

顺着这条线还挖出一个**真缺陷**（不只是测试问题）：

> `LeftoverSafetyGuard.Check` 的第一道闸门写的是 `if (!Path.IsPathRooted(raw)) return "不是绝对路径";`
> 但 `Path.IsPathRooted("D:")` 返回 **true**——驱动器相对路径也算 "rooted"。
> 于是 `"D:"` 能通过这道闸门，接着被 `GetFullPath` 补全成 `D:\<某目录>`，
> 后面的层级/保留名/保护路径判断全部作用在一个**语义不确定**的路径上。
> 在 `=D:` 不存在的环境里，`"D:"` 会被补全成 `D:\`，那是一条**盘根**——
> 而"盘根绝不能删"这道闸门此时排在它后面，靠 `IsVolumeRoot` 兜。
> 换句话说：**两道闸门对同一个输入给出了互相矛盾的判断，其中一道排错了位置**。

修法（Lead 直接改，两处）：

1. `IsVolumeRoot` 先看**原始输入**是否完全限定，驱动器相对形态一律返回 false（与环境无关）；
2. `Check` 的第一道闸门补成 `!Path.IsPathRooted(raw) || !Path.IsPathFullyQualified(raw)`，
   让 `"D:"` 在**补全之前**就被"不是绝对路径"拦下（与 v0.3 那条"必须先判原始输入"的教训同源，见进度文档第 24 条缺陷）。

新增 4 项回归用例（`LeftoverSafetyGuardTests` 29 → 33）：`C:` / `D:` / `Z:` 三个驱动器相对形态各一条 Theory，
外加一条断言 `Check("D:")` 给出的原因必须是"不是绝对路径"而不是误导性的"这是盘符根目录"。

> 这也是一个"文档里的数字必须真跑"的例子：如果我只抄 v0.4.0 日志的 421，
> 就不会发现换个目录跑会挂。

## 五点五、又一条：启动期的 XamlParseException 不是 XAML 的锅

`app-dev` 反馈有人在启动时撞到：

```
XamlParseException: 'Provide value on System.Windows.StaticResourceExtension' 引发异常
  行号 10，行位置 11 → Background="{StaticResource BackgroundBrush}"
```

我先自己核对了一遍结构，确认结论成立，然后才写进文档：

- `MainWindow.xaml` 第 10 行确实是 `Background="{StaticResource BackgroundBrush}"`；
- `BackgroundBrush` 定义在 `Themes/Styles.xaml`（第 14 行，由 `BackgroundColor` 派生）；
- 它**只**通过 `App.xaml` 第 8 行的 `MergedDictionaries` 注入应用级资源。

所以任何绕开 `App.InitializeComponent()` 直接 `new MainWindow()` 的加载方式都会抛这条错——**必然复现，与代码无关**。
实际触发场景是「构建刚结束、程序集还没写完就启动」的竞态。

**这条值得写进文档的理由不是它多严重，而是它浪费排查时间**：
看到 `StaticResource` 报错，人的第一反应是去查资源字典缺了哪个键——而正确答案是"等一下再启动"。
写下来，下一个人就不用再走一遍。

## 六、这一版的方法论

v0.4.0 的日志里写过一条教训："调研的成本远低于返工的成本"。
这一版补一条：**"代码通过"和"文档自洽"之间还有一段路，而且这段路会反过来暴露代码问题**。

证据就是上面第四节那个坑——只有真的换个环境跑一遍，才会发现某条用例对环境有隐含依赖。
文档收口不是"事后写作文"，它是一次强制自查：每写下一句"支持 32 位视图"，
就必须能指出代码里哪几行支持它；指不出来，就说明这句话该写"待实测"。
