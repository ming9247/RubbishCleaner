# 2026-10-24 开发日志 —— v0.1.2 失效启动项检测

## 起因

用户反馈两条扫描结果：

1. **WorkBuddyAI** —— "安装国内版 WorkBuddy 会出现两个版本的图标"
2. **AdskAccessService** —— "Adsk 那个是自启动的云服务"

用户最初的意思是"这种不用改算法，加白名单就可以了"。我去核了实际数据，发现第一条的判断依据是错的。

## 核实结果：WorkBuddy 是"僵尸启动项"，不是"可疑软件"

```
Run 项 1: D:\workbuddy-internate\WorkBuddyAI\WorkBuddy.exe  → 不存在
Run 项 2: D:\WorkBuddy\workbuddy\WorkBuddyAI.exe            → 不存在
实际在跑: D:\WorkBuddy-CN\WorkBuddy.exe                      → 存在（9 个进程）
```

**两条启动项指向的文件都不存在。** 国内版装到了 `D:\WorkBuddy-CN\`，
但注册表里还留着两个旧路径的 Run 项——升级/换目录时的经典残留。

所以用户看到的"两个版本图标"不是两个版本在共存，而是**两个指向已删路径的僵尸项**。

原实现把它们算成 70 分"疑似"，理由是：无桌面图标 + 无开始菜单 + 未签名。
但**程序根本不存在**，这三条全是伪信号。它真正的问题是"该清理"。

> 如果我按用户最初说的"直接加白名单"，会把这些标成"白名单/正常"，
> 僵尸项继续留在注册表里每开机尝试加载一次，而工具再也不会提醒。
> 这会把一个真问题掩盖掉，所以我先去核了数据，再回头和用户确认处理方式。
>
> 用户改选了"按残留处理"，这比白名单更对。

## 做了什么

### 1. 失效启动项建模

- `StartupEntry.TargetExists` / `IsOrphan`：目标文件不存在即判定失效
- `SoftwareProfile.IsOrphaned` / `OrphanEntries`：支持"部分失效"
- 新增评分规则 `ORPHAN_STARTUP`，**权重 0**

权重为什么是 0：失效项不是"风险"，是"待办"。给它加分只会制造噪声。
它的价值在于被**单独标记出来供清理**。

失效时，`NO_VISIBLE_WINDOW` / `NO_DESKTOP_ICON` / `NO_START_MENU` / `UNSIGNED`
全部标记为**不适用**，只剩 `AUTOSTART` 计 30 分 → 归为"正常"。

### 2. 判定边界：只认绝对路径

计划任务与服务的命令行常写成裸文件名（`BthUdTask.exe`、`WsxService`），
由系统按 System32 解析。若把这类相对路径也判为"不存在"，
会把大量正规系统任务误报成残留——这条我在写之前就想到了，加了守卫也加了测试。

### 3. 正规厂商签名白名单

按用户选择，只按签名加，不按名字加：

```
signer: Autodesk          → AdskAccessService / AdskAccessCore / AdskLicensingService ...
signer: Tencent Technology
signer: NVIDIA Corporation / Intel Corporation / Realtek Semiconductor
signer: Adobe Inc. / Mozilla Corporation / Oracle America / ByteDance
```

理由：按名字维护是打地鼠，按签名才是稳定判据；而且产品文档本来就要求
"知名厂商签名 → 直接标安全"。

### 4. UI

- 左侧新增「清理」分组：「残留启动项（N）」，可一键筛出
- 状态列：失效时显示"启动项已失效"（琥珀色加粗），而不是"未运行"
- 统计栏加「残留 N」
- 证据链列出具体路径与注册表位置

## 实测效果

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| 高风险 | 1 | 1 |
| 疑似 | 19 | 9 |
| 正常 | 97 | 109 |
| 残留启动项 | 未识别 | **6 条**（管理员权限扫描） |

`WorkBuddyAI` / `WorkBuddy`：70 分"疑似" → 30 分"正常 + 启动项已失效"。
额外还揪出一条 `WsxService` 服务残留（指向 `D:\nexus\Winstep\WsxService`）。

## 踩的坑

### 坑 1：改行为后 6 个测试集体失败

改完评分立刻跑测试，`Score_AllHeuristicFeaturesHit_IsCappedAt100` 等 6 个失败。
原因：测试用的假路径 `C:\Apps\app.exe` 本来就不存在，现在被判定为失效启动项。

这不是 bug，而是**测试数据依赖了真实文件系统的偶然状态**。
修法不是改断言，而是给 `StartupEntry` 加 `TargetExistsOverride`，
让测试能显式声明"这个程序存在"。评分测试本来和文件系统无关。

### 坑 2：「残留启动项」按钮永远是灰的

`RelayCommand` 的 `CanExecute` 依赖 `OrphanCount`，构造时是 0（按钮禁用）。
扫描完成后虽然 `OnPropertyChanged(nameof(OrphanCount))` 了，
但 `CanExecute` 不会自动重新求值——需要 `CommandManager.InvalidateRequerySuggested()`。

### 坑 3：又是 UI 自动化的坑（第三次）

想点「残留启动项」按钮验证筛选，坐标点击静默失败。
根因是 **UIPI**：主程序以管理员运行，普通权限的合成鼠标输入会被直接丢弃。
（前两次分别栽在 `MainWindowHandle` 抓错窗口、UIAutomation 跨完整性级别找不到元素。）

这次换了思路：不再硬刚 UI 自动化，而是写集成测试**直接驱动 `MainViewModel`**——
`await vm.ScanAsync()` 后用真实扫描结果验证筛选、计数、文案。4 个测试，
覆盖了筛选正确性、失效项不判高风险、切回「全部」能恢复。

教训：**能被逻辑测试覆盖的东西，不要用 UI 自动化去验。**

## 下一步

v0.2 卸载引擎之前，可以先把「残留启动项」做成可操作的：
现在只能"看见"，还不能"删除"。这属于 v0.4 注册表清理的一部分，
但只针对失效启动项做删除，风险很低、价值很高。
