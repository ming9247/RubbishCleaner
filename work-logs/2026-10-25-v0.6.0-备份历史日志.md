## 二、备份历史：不建索引，从文件反推

备份目录（%LocalAppData%\RubbishCleaner\registry-backups）本身已是事实的单一来源。
建索引迟早失同步（用户手动删文件后索引就是谎言）。所以 BackupHistoryStore 只做解析：

- 文件名 orphan-{键名}-{yyyyMMddHHmmss}.reg → 时间戳（解析失败回退文件修改时间）；
- 段头 [HKEY_...] → 键路径（物理路径，32 位视图含 WOW6432Node）；
- "DisplayName"="…" 值行 → 展示名。

## 三、回滚的三层防线，与真机暴露的第四个坑

1. **前置检查**：目标键已存在 → 拒绝。备份是「删除前的原样」，
   但从备份到回滚之间键可能被重建——import 会覆盖它；
2. **reg import**：与用户双击 .reg 完全同路径。不用 RegistryKey API 自己写回——
   那等于第二套写注册表的实现，UTF-16LE / WOW6432Node / 递归子键每个坑都要重踩；
3. **复核**：键必须真的回来。写操作不以退出码为准，以注册表实际状态为准。

**第四个坑是真机验证暴露的**：第一版的默认键存在性检查只开 LocalMachine 基键。
单测全绿（测试注入假委托），真机一跑——HKCU 的备份复核永远失败、
重复回滚的防线永远失效。hive 必须来自段头原文，这与 ADR-049（32 位视图还原落点）
是同一类教训：**注册表操作必须区分 hive/view，任何「默认机器」的假设都会在 HKCU 上翻车**。

顺带修掉的设计缺陷：第一版「回滚前检查」与「回滚后复核」共用同一个 keyExists 委托——
前者要求键不存在（防覆盖）、后者要求键存在（确认成功），语义自相矛盾，
两条测试互斥失败。拆成 preRollbackKeyExists / postImportKeyExists 两个独立依赖。

## 四、UI 的两个时序坑（都是测试锁死的）

1. **回滚后的刷新被防重入吞掉**：RefreshAsync 有 IsBusy 防重入，
   而回滚的 try 块里 IsBusy 还是 true——先解除再刷新，否则刷新静默 return；
2. **回滚结论被刷新覆盖**：刷新把 StatusText 覆盖成"读取到 N 个备份"，
   用户看不到回滚结果——回滚结论必须写在刷新**之后**。与 v0.3 缺陷 26 同源
   （清理结论被"扫描完成"覆盖），但这次测试先于提交发现。
