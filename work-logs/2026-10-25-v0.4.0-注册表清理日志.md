# 2026-10-25 开发日志 —— v0.4.0 注册表清理（孤儿 Uninstall 条目）

## 目标

v0.4 清理注册表残留。这是风险最高的一版：文件删错了能从回收站还原，
注册表键删错了，轻则软件报错，重则系统组件加载失败。所以第一件事是**划边界**。

## 一、范围：只做「MSI 孤儿 Uninstall 条目」

| 做 | 不做 |
|---|---|
| `Uninstall\{GUID}` 下 MSI 已不存在的产品 | `HKCR` 任何键（COM 引用） |
| 删除前强制 `.reg` 备份 | `HKLM\SYSTEM`（驱动/服务） |
| 删除后立即复核 | 厂商根目录（归属不明） |
| | 孤儿 CLSID / 文件关联（需解析 COM 引用计数，误报率不可接受） |

## 二、调研阶段：草案的判据被真机推翻

起草时我写的判据是「`Classes\Installer\Products\{GUID}` 不存在 = 僵尸」。
用 CC Switch 做真实样本一查，结果完全出乎意料：

| 检查项 | 结果 |
|---|---|
| `MsiQueryProductState` | **5 = INSTALLED** |
| `MsiEnumProducts` 包含该产品 | **True**（共 344 个） |
| `LocalPackage` | **`C:\Windows\Installer\c5d6cb5d.msi` 存在** |
| `Classes\Installer\Products\{GUID}` | False |
| `UserData\<SID>\Products\{GUID}` | False |
| `reg query HKLM\SOFTWARE /s /f {GUID}` | **0 命中** |

**产品完全有效，但标准注册表键全都不存在。**

如果按草案的判据上线，会把一个好好安装着的软件判成孤儿并删掉它的卸载入口。

### 教训

这次是**在写代码之前**做的调研，所以只浪费了一份设计草案，没有浪费一行生产代码。
对比 v0.3.1 那次：先写完、单测全绿、才做真机验证，结果炸出 3 个缺陷。

**调研的成本远低于返工的成本。**

## 三、修正后的判据：只信 Windows Installer 自己的回答

两条同时成立才是孤儿：

1. `MsiQueryProductState(guid)` 返回 ABSENT
2. `MsiEnumProducts()` 的列表里没有它

### 又一个坑：ABSENT 有三种形态

第一次真机 E2E 跑出来 **0 个孤儿**——明明自己造了一个。

查下来 `MsiQueryProductState` 对**从未安装过**的 GUID 返回的不是 1/2/3，而是：

| GUID 类型 | 返回值 | 含义 |
|---|---|---|
| 曾装过、已卸载 | 1 / 2 / 3 | ABSENT |
| **从未装过** | **4294967295** | ERROR_UNKNOWN_PRODUCT |
| 格式非法 | 4294967294 | ERROR_INVALID_PARAMETER |
| 正常安装 | 5 | INSTALLED |

而「从未装过」恰恰是**最常见的孤儿形态**（注册表里有条目，Windows Installer 数据库里根本没这个产品）。
我第一版只判了 1/2/3，把最主要的一类全漏了。

## 四、七道闸门

| # | 闸门 | 理由 |
|---|---|---|
| R1 | 键名必须严格匹配 `{8-4-4-4-12}` | 防止误删非 GUID 键 |
| R2 | 拒绝 `Uninstall` 根键 | 删它等于清空整个已安装列表 |
| R3 | 必须在标准 `Uninstall` 路径下 | 防止路径拼接错误 |
| R4 | 执行前**重新查** MSI 状态必须是 ABSENT | 扫描到确认之间产品可能被重装 |
| R5 | 再确认不在 `MsiEnumProducts` 列表 | 两个 API 打架时不删 |
| R6 | **备份必须成功且非空**，否则不删 | 这是底线 |
| R7 | 删除后复核键确实不存在 | 与 `RegistryWriter` 同一约定 |

## 五、关键设计选择：这次允许删键

v0.1.3 清理 Run 启动项时坚持「只删值不删键」（ADR-019），因为一个 Run 键下挂着多个软件的值。

但 `Uninstall\{GUID}` 是**一个产品一个键**，键下所有值都属于这个产品，删键是安全的。
这个区别写进了代码注释，避免后来者统一成同一套规则。

## 六、命名空间踩的坑

把新代码放在 `RubbishCleaner.Core.Registry` 命名空间，结果旧测试全炸：

```
StartupCleanerExecuteTests.cs(75): 命名空间 RubbishCleaner.Core.Registry 中不存在类型 CurrentUser
```

原因：`using RubbishCleaner.Core.Registry;` 之后，`Registry.CurrentUser` 被解析到我们自己的命名空间，
而不是 `Microsoft.Win32.Registry`。

改名 `RubbishCleaner.Core.RegistryCleanup` 后正常。**教训：不要用会和 BCL 类型同名的命名空间。**

### 真机 E2E（提权）

```
阶段1：造测试条目 {DEADBEEF-...}（WindowsInstaller=1，GUID 不在 MSI 库）
阶段2：扫描 344 个 MSI 条目，发现 1 个孤儿
  OK 命中：RcTest 孤儿条目
    · Windows Installer 报告该产品未安装：未知产品
    · 该产品不在已安装产品列表中（MsiEnumProducts 交叉验证）
    · 应用和功能列表里仍保留此条目
    · 记录中的安装位置：D:\NoSuchDir\RcTest（目录已不存在）
阶段3：CC Switch 被判为孤儿？ 否（正确，产品仍有效）
阶段4：计划清理 1 项 → 删除成功 → 清理后条目还在？ 否
阶段5：备份 orphan-{DEADBEEF-...}.reg (788 字节)
        reg import 退出码=0
        DisplayName/DisplayVersion/Publisher/InstallLocation/UninstallString/WindowsInstaller 全部一致
阶段6：现场已清理
```

**在 344 个条目里只报了这 1 个**——CC Switch 及其他 343 个都没被误报。

### 备份可还原的实质验证

单测里有一条 `Write_BackupCanBeReadBackByRegImport`：
造键 → 导出 .reg → 删键 → `reg import` → 断言值一致。
这是「可还原」的实质证明，而不是「写出了个文件」就算过。

## 八、没做的与已知风险

1. **UI 层的端到端点击验证没做成**：本机提权窗口的 UIA 自动化不稳定（v0.1 就踩过）。
   UI 逻辑由 112 个 App 单测覆盖，Core 链路已真机验证。
2. **`MsiEnumProducts` 的 32/64 位视图**：当前用默认视图枚举，
   理论上可能把纯 32 位产品误判。本机 344 个产品未复现，但多用户机器上需再验证。
3. **每用户安装的产品**：`MsiQueryProductState` 按当前用户视角判断。
   多用户机器上别的用户装的产品可能返回 ABSENT——这种情况会被 R5（枚举交叉验证）挡住，
   因为 `MsiEnumProducts` 也按当前用户枚举，两者一致时才会删。**但这是推测，未实测。**
4. **真实僵尸样本没找到**：本机 343 个 MSI 条目全部有效。E2E 用的是程序化造的样本。
   造样本能验证代码路径，但**不能证明判据在真实脏环境里同样可靠**。

## 九、给下一版的提醒

2. v0.4.1 可以补：**孤儿条目的 32 位视图枚举** + 多用户场景验证。
3. 这一版证明了「调研先于编码」的价值。v0.5 如果做 CLSID/文件关联，
   **必须先花一天做调研**，不要直接写代码。
