## 目标

## 二、第一次卸载：直接失败，暴露一个潜伏半年的 bug

```
SNAPSHOT files=2 dirs=0 bytes=34206137    ← 快照正常
UMINSTALL started=False completed=False
  msg=启动卸载程序失败：找不到 'MsiExec.exe /X{09CC399B-...}'
```

### 根因

`UninstallExecutor.BuildStartInfo` 用 `RegistryTextSanitizer.TryExtractExecutable` 取可执行文件，
而该方法**刻意**对 `MsiExec.exe /X{...}` 返回 `null`——它的职责是"取出可校验的 exe 路径"，
而 MSI 没有独立可校验的 exe（v0.2 有单测 `TryExtractExecutable_MsiExec_ReturnsNull` 锁着）。

于是 fallback 走了 `FileName = command`（整条命令行）、`Arguments = ""`，
`Process.Start` 就去找一个名叫 `"MsiExec.exe /X{...}"` 的文件，必然找不到。

### 影响面

**本机 27 个 MSI 软件全部无法卸载。**

这个 bug 从 v0.2 就存在。v0.2 的工作日志里其实写了：
> 没有真正执行一次卸载。原因：本机 114 个软件都是有主的……

**当时就知道没验证，但没把它当成风险，只当成了"遗憾"。**
这次真机一跑就炸，说明"没验证"等于"大概率是坏的"。

### 修法

新增 `SplitCommand`，按三种形态正确拆分：

| 形态 | 示例 | 拆分结果 |
|---|---|---|
| 引号包裹 | `"C:\Program Files\App\uninst.exe" /S` | `(C:\Program Files\App\uninst.exe, /S)` |
| 含 .exe | `MsiExec.exe /X{GUID}` | `(MsiExec.exe, /X{GUID})` |
| 仅命令名 | `cmd /c del` | `(cmd, /c del)` |

顺带修正：只对**绝对路径**设置 WorkingDirectory。MsiExec 这类系统工具交给系统解析，
强行设成别的目录反而会让它找不到依赖。补了 9 项回归测试。

## 四、用 v0.3.1 扫这个真实残留

### 又发现两个缺陷

**缺陷 A：`.cc-switch` 完全没被扫到**

`LeftoverScanOptions.DefaultRoots()` 只含 Program Files / ProgramData / AppData，
**不含用户主目录**。而 Unix 风格工具把配置放在 `~/.xxx`——
本机主目录下有 **24 个点目录**（`.cc-switch`、`.codex`、`.config`、`.nuget`…）。

修法：把 `SpecialFolder.UserProfile` 加入默认根目录。

**缺陷 B：`D:\CCswitch` 被闸门拦住，理由"层级过浅（2 级）"**

`D:\CCswitch` 天然只有 2 级（盘符 + 目录名），但它是完全合法、该被清理的残留。
要求 ≥ 3 级会把"装在盘根下"的软件全部判成不可清理。

真正危险的 `C:\Program Files` 应该由**保留名**拦住，而不是靠层级。

修法：保留名判断前置；层级门槛改为只拦"盘根直接子目录"。
补 4 项测试（`D:\CCswitch` 应放行 / `C:\Windows` 仍拒绝 / `C:\Program Files` 拒绝理由是保留名）。

### 修复后的扫描结果

```
  D:\CCswitch                              32.6 MB / 2 文件    High
  %LocalAppData%\com.ccswitch.desktop      34 MB / 365 文件    High   ← 手工调查时漏掉的
  %AppData%\com.ccswitch.desktop           215 字节 / 1 文件   High
  %USERPROFILE%\.cc-switch                 821 KB / 7 文件     High
  合计 67 MB
```

**`com.ccswitch.desktop` 那 34 MB 是意外收获**：我手工查残留时只看了 `.cc-switch`，
完全没注意到 Electron 应用把 365 个文件的数据放在 LocalAppData 里。
定向扫描的"按名字匹配常见位置"这一步自动找到了它，而且证据链说得很清楚。

## 六、这一轮真正的价值

一个真实卸载，炸出 **3 个缺陷**，其中第 1 个是**影响 27 个软件功能完全不可用**的 P0：

| # | 缺陷 | 为什么单测发现不了 |
|---|------|------------------|
| 1 | MSI 卸载把整条命令行当文件名 | 单测只测了"拒绝路径"，没测"真的启动一个 MSI" |
| 2 | 主目录不在扫描根目录里 | 造样本都放在 AppData 下，没覆盖 `~/.xxx` |
| 3 | 盘根残留被层级闸门误拦 | 造样本都在 Program Files 深层，没覆盖盘根 |

**共同点：三个都是"我的样本没覆盖到的形态"。**
造样本时人会下意识挑"典型"位置（Program Files 深处、AppData 下），
而真实软件的安装位置五花八门（盘根、用户主目录、Electron 的 com.xxx 目录）。

## 八、给 v0.4 的提醒

1. **僵尸 Uninstall 条目**：`WindowsInstaller=1` 但 `Classes\Installer\Products\{GUID}` 不存在，
   这就是判定"孤儿注册表键"的一个可靠信号。本机现在正好有一条真实的（CC Switch）。
2. **别再重复"造样本代替真实验证"的错误**。这一轮的三个缺陷全是造样本覆盖不到的形态。
3. 卸载流程还有个未验证的点：**MSI 卸载 UI 弹出时，本工具会一直等到超时**。
   用户取消卸载时 `fAnyOperationsAborted` / 退出码怎么处理，需要单独验证。
