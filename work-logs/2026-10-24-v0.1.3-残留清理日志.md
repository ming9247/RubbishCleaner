# 2026-10-24 开发日志 —— v0.1.3 残留启动项可清理

## 目标

v0.1.2 能"看见"残留但还不能"删"。这次把最后一步补上：
让用户能真的清掉那些指向已删除文件的僵尸启动项。

这是本项目**第一个会写注册表的功能**，安全要求远高于之前所有改动。

## 做了什么

### 1. 精确的注册表坐标

新增 `RegistryAnchor(Hive, View, SubKeyPath, ValueName)`，在扫描时由 `RegistryRunSource` 填充。

**为什么不解析 `Location` 字符串**：那是个给人看的字段，格式可能变（比如加个前缀），
而删除是不可逆的。用强类型记录目标，测试能逐字段断言，编译期就能发现漏字段。

### 2. 六道安全闸门

| # | 闸门 | 作用 |
|---|------|------|
| 1 | 只选失效项 | `IsOrphan` 为 false 的连"跳过"都不算，根本不进计划 |
| 2 | 只允许 Run/RunOnce | 服务、计划任务进 `Skipped` 并说明原因 |
| 3 | 要求精确坐标 | 缺 `RegistryAnchor` 的拒绝 |
| 4 | **执行前重新校验** | 扫描→确认之间程序可能被重装，此时跳过 |
| 5 | **先备份，失败即中止** | 备份生成不了就一条都不删 |
| 6 | 只删值 + 删后复核 | 绝不 `DeleteSubKeyTree`；删完重新读一遍确认 |

第 4 条是我觉得最容易被忽略的：用户可能开着工具去把软件装回来了，再回来点"清理"。
如果信任扫描时的旧结果，就会删掉一个刚刚恢复正常的启动项。

### 3. 备份用标准 .reg

`%LocalAppData%\RubbishCleaner\backups\RubbishCleaner-启动项备份-<时间戳>.reg`

为什么不用自定义 JSON：**用户不装本工具也能用 `reg import` 还原**。
这是"可恢复性"最强的保证——备份的意义就是"最坏情况下还救得回来"，
如果还原依赖本工具本身，那就不算真备份。

文件必须 UTF-16 LE 带 BOM，否则中文路径导入会乱码。

## 踩的坑

### 坑 1：测试第二次跑就失败了

`CleanOrphans_WhenUserCancels_DeletesNothing` 第一次通过、第二次失败。
原因：第一次测试真的把机器上的 Run 类残留删干净了，第二次跑时没有残留，
所以根本没进确认步骤。

这暴露了一个测试设计问题：**测试依赖了机器的当前状态**。
改成先精确判断"是否存在可清理项"（`IsOrphan && RegistryAnchor != null && Run 类`），
没有就跳过——而不是假设"有残留就一定能清理"。

### 坑 2：'有残留' ≠ '可清理'

诊断时发现：`OrphanCount = 1` 但清理命令提示"无可清理项"。
一开始以为又是命令可用性的 bug，查下来发现是 `Winstep Xtreme Service`——
一条服务类残留，被 `BuildPlan` 正确拒绝了。

**这不是 bug，是安全闸门在正常工作。** 但说明我原来的测试断言写错了：
用 `OrphanCount > 0` 当"应该弹确认框"的前提是错的，得用"可清理项数量"。

顺带发现：上一个版本里 `AdminViewModel.OrphanCount` 的语义是"失效启动项总数"，
而"可清理数"是它的子集。UI 文案上应该区分，否则用户会困惑
"为什么显示 4 条却点不了清理"。这条留给下次优化。

## 测试

165 项（Core 95 + App 70），新增 26 项，其中安全性测试占大头：

- `BuildPlan_ExcludesEntriesWhoseTargetStillExists` —— 目标还在就不进名单
- `BuildPlan_OnlyTakesOrphanedEntriesFromMixedProfile` —— 混合画像只取失效那条
- `BuildPlan_RejectsNonRunKindsAndExplainsWhy`（4 个 InlineData）—— 拒绝服务/任务并给原因
- `Execute_SkipsTargetWhoseFileReappeared` —— **执行前重新校验**
- `DeleteValue_MissingValue_ReturnsFailureNotSuccess` —— 不能把"没删到"报成成功
- `DeleteValue_EmptyValueName_IsRefused` —— 拒绝删默认值
