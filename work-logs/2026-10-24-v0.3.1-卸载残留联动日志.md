# 2026-10-24 开发日志 —— v0.3.1 卸载与残留联动

## 目标

v0.3.0 做的是"不知道卸过什么"的通用残留扫描。这一版补另一半：
**用户刚刚用本工具卸载了 X**——这时软件名、安装位置、卸载前有哪些文件全是已知事实，
能做出确定性的残留清单，而不是启发式猜测。

## 一、设计：为什么这一版的值钱

| | v0.3.0 通用扫描 | v0.3.1 定向扫描 |
|---|---|---|
| 知道卸过什么吗 | 不知道，靠硬痕迹推断 | 知道，软件名/安装位置是事实 |
| 判定强度 | 启发式（孤儿卸载程序 / 失效启动项） | 确定性（快照对比 + 已知软件名） |
| 误报风险 | 有（已压到本机 1 例且被闸门拦住） | 几乎没有 |
| 触发方式 | 用户手动点扫描 | 卸载完成后自动 |

**但有个坑差点踩**：第 3 步（按软件名在 %AppData% 找同名目录）看起来跟 v0.3.0
"按名字猜残留"是同一件事。区别在于：通用扫描里"不知道卸过什么"，
306 个顶层目录里 285 个对不上任何已装软件，按名字判残留误报率 93%；
而这里"刚刚卸了微信"是事实，"%AppData% 下还有 WeChat 目录"这条推理成立。

所以名字匹配在 v0.3.0 里被禁、在 v0.3.1 里被允许，**理由是相反的**。
仍然加了保守约束：短名字（< 4 字符）只允许全等，否则"微信"会匹配到"微信小程序"。

## 二、踩的坑

### 坑 1：连续 Save 多个快照，按文件时间排序会随机删错

`Prune` 一开始按 `File.GetLastWriteTimeUtc` 排序保留最近 N 份。
单测连续写 5 份快照，结果**最新的那份被删了、旧的留下了**——5 个文件写入落在同一毫秒。

修法：排序键改成**文件名里的 yyyyMMddHHmmss**（字典序即时间序，稳定且不用读文件）。

### 坑 2：假环境不知道"根目录"，第 3 步整个被跳过

单测里假环境只注册了"匹配到的目录"，没注册"常见位置根目录"。
而第 3 步的逻辑是先 `DirectoryExists(candidateRoot)` 再枚举子目录，
于是整个第 3 步被静默跳过，测试断言 `Assert.Single(result.Directories)` 失败。

**这不是产品缺陷，是测试搭建问题**，但暴露了一个真实语义：
假环境必须完整模拟"目录树存在"，而不只是模拟"我关心的那个目录存在"。

### 坑 3：两字中文软件名被 Variants 的长度门槛挡掉

`SoftwareNameNormalizer.Variants` 原本要求 `full.Length >= 3`，
于是"微信"（2 字）返回空集合，第 3 步永远匹配不到它。

中文软件名大量是两个字（微信、钉钉、抖音），一刀切要求 3 字会把它们全漏掉。
修法：阈值降到 2，但把防误报的责任**转移给调用方**——短名字只允许全等匹配。

### 坑 4：反射调私有 async 方法拿到 object，编译期调不了 GetAwaiter

单测要验证"发现残留就抛 ResidueFound 事件"，得反射驱动私有的 `ReportResidueAsync`。
`method.Invoke(...)` 返回 `object`，直接 `.GetAwaiter()` 编译不过。
修法：`((dynamic)method.Invoke(...)).GetAwaiter().GetResult()`。

### 坑 5：`Leftovers` 在 MainViewModel 上，不在 AppsViewModel 上

写单测时想当然写成 `vm.Leftovers.ShowUninstallResidue(...)`，编译不过。
这反而是对的：软件页不该持有残留页，否则两个页签互相依赖。
改成构造独立的 `LeftoversViewModel` 测展示逻辑。

## 三、编排：为什么拆成两层接口

```
AppsViewModel ──CaptureBefore/ScanAfterAsync──► IUninstallResidueCoordinator
      │                                              （接口，可假）
      └──ResidueFound 事件──► MainViewModel ──► LeftoversViewModel.ShowUninstallResidue
```

1. **协调者走接口**：为 null 时整条链路静默关闭，v0.2 的卸载流程一行逻辑都不用改。
2. **结果走事件**：软件页不直接引用残留页 ViewModel，否则两个页签互相持有，改一个坏一个。

两条都是"改动不要扩散"的老原则，但这次是**真的需要**——
v0.3.1 动的是 v0.2 已经跑通的卸载流程，任何耦合都可能让它回归。

```

HAS_RESIDUE=True
```

## 五、没做的

- **没在 UI 上加"跳转到残留页"的自动切换**：卸载完弹一堆东西会更烦。
  目前是残留页自己更新（`HasPendingResidueHint` 已留好属性但没接角标）。
- **没做文件内容级对比**：只对比"条目在不在"，卸载器改写同名文件发现不了（刻意）。
- **没接真实卸载流程的真机验证**：本机 115 个软件都是有主的，不能真卸。
  造样本验证的是扫描与快照逻辑，编排链路由 10 项单测覆盖。

## 六、给下一版的提醒

1. **v0.3.1 的编排链路没有真机走过完整一圈**（卸载 → 快照 → 扫描 → 展示）。
   建议先用一个不重要的软件试一次，重点看：卸载器弹窗会不会挡住 2 秒等待、
   `%AppData%` 下匹配到的目录是否真的是那个软件的。
2. **快照文件会越攒越多**（虽然每个软件只留 3 份）。如果以后支持多用户，
   要考虑按用户隔离目录。
3. v0.4 注册表清理仍然是最危险的一版，且它和残留扫描共用"认领"概念——
   到时候要考虑把 `ClaimPaths` 的构造逻辑抽出来共享，别复制第二份。
